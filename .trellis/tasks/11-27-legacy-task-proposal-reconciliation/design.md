# 旧任务与未决提案的人工核对方案

适用对象是从协作上线前的 `0043` 遗留的章节生成任务和智能体提案。C8 的新版基线是 `b7b3d248`（`0070`），本次代码核对基线是 `ac97d4d`。历史演练、当前代码回归和还需在目标副本验证的操作分别列在下文。

## 1. 先确认是哪一种遗留

| 场景 | C8 实际观察 | 能据此作出的决定 |
| --- | --- | --- |
| 升级前已排队的章节生成 | 双库中本人取消 409；管理员取消 202 后 12 秒仍 queued，章节 generating；重发 409 | 保留取消操作号，继续核对后台结果；等待时间和 202 都不能证明退出 |
| 升级前正在生成的章节 | 新版启动后任务 interrupted，章节 generating；本人、管理员取消及重发均 409，重试报 task_actor_unavailable | 分开记录任务、执行进程和章节；中断标记不足以恢复原稿状态 |
| 旧版网页取消待审核智能体任务 | SQLite 独立网页复做中任务已取消，原提案仍待确认，按钮不可用 | 留存同一提案和目标业务数据，原提案仍计为未决 |
| 升级后取消并发送新消息 | 双库中旧 paused 任务可取消；本人同会话发送新消息后新任务成功并调用模型，原提案仍 proposed。未取消时另在独立副本尝试继续、结束、整轮拒绝和发新消息，均 409 | 核对原提案与新轮次各自的结果；不能用新任务成功核销原提案 |

依据见 [C8 双库矩阵及最终日志索引](../archive/2026-11/11-20-collab-migration-deploy-drill/research/verification.md) 和 [旧版独立复做](../archive/2026-11/11-20-collab-migration-deploy-drill/research/readme-independent-verification.md)。取消矩阵使用运行时在线快照，智能体专项使用正常退出快照，另有强杀旧进程后的章节冷快照。观察窗口有限，结果不能推到所有任务或所有版本。

## 2. 现场只读核对

1. 按 [0043 升级与回滚步骤](../../../README.md#从-0043-升级作品协作) 保持维护，阻止用户、开放 API 和后台写入。记录部署版本、数据库实例、快照时间和校验值。保存当前库、日志和升级前最终快照，分别在独立目标验证可恢复性。不要让旧程序连接升级后的库。
2. 按部署清单逐台核对旧应用、调度器、工作进程、重载父子进程、外部调用及数据库写入方。记录实例、退出时间、是否会自动重启。端口消失、心跳过期、模型暂时没有输出只能佐证；任一实例失联、外部结果不明或仍有写入，就保持维护。
3. 在受控只读副本记录作品、章节、任务种类／ID／稳定键、入队轮次、状态、执行键、工作者及其工作记录、取消操作号。对照同章及同串行键的新旧任务，记录章节状态、正文修订、正文及场景摘要、版本历史和三项占用字段。分别说明“谁还能写”“任务是否收尾”“章节应回到何状态”，缺失项记为未知。原状态须由生成前同一章节、同一基线的可靠记录证明；有正文不能推出 done，空正文不能推出 draft。
4. 由有权查看原会话的人记录原会话、原消息、提案及目标资源。比对工具调用 ID、原参数和预览的受限摘要、原轮次、状态、result、effects、执行时间，以及目标正文版本、子任务或外部系统回执。升级前按同一快照来源追踪旧行，升级后同时记录 change_key；独立迁移的两个克隆可能分配不同 UUID。只在原权限范围保存原内容，维护记录仅列定位信息、摘要和结论。无回执或内容碰巧相同都不足以证明外部操作从未发生。

## 3. 章节处置

**有已验证的升级前最终快照。** 优先在空库或新 SQLite 文件恢复快照，用配套旧代码、配置和原密钥核对章节与任务。若快照本身尚有活动任务，只能在受控副本观察旧版正常完成或经正常取消确实收尾；再次核对任务终态、正文版本、章节状态和待审核提案。仍不一致就停止。切换前须明确新版独有写入怎样保留；整库回滚不会自动合并这些数据。本次双库对照验证了排空快照的恢复。原提案在恢复后仍未决，升级后新增的作品只出现在保留的新版副本。任意未排空快照能否清除卡住的任务，仍需逐案核对。[回退对照及原始日志](research/restore.md)

**无可用快照，或快照不能安全收尾。** 保留当前库及核对记录，将受影响任务和章节列为未解决。当前版本提供作者修改生成中章节状态的入口，服务按行锁和当前占用字段条件更新，可恢复 draft 或 done；它既不终止任务，也不核实旧进程退出。当前编辑器对来源未知的章节只提示到任务面板核对。对仍 queued、取消待处理、存在后继任务／新占用、无法证明旧执行体退出或原章节状态的记录，不调用该入口试错。不得补填 actor、worker、execution 或 claim，也不按章节 ID 清队列。

**真实冷快照的额外发现。** 在本次单任务副本中，接管进程将旧生成任务置为 interrupted，留下 worker_key 和项目级 abort_failure/failed 记录。后者没有 task_id、task_key 或执行凭据，不能靠它证明具体任务已退出。现场若只能看到这些数据库字段，就停在只读核对。实验另有操作系统和受控模型的直接证据：旧进程组已消失、旧调用在输出前关闭、接管进程也已退出并留下 stopped_at；库内无执行槽、其他任务或新章节占用。失败记录在整个复位过程原样保留。能恢复章节状态，不代表项目清理失败已经解决。

**隔离副本上的单字段复位。** 仅针对旧任务已经中断、所有原写入方已确认退出、没有新占用／在途工作、能证明目标状态的个案。从最后一次只读核对起，直到写入及复核结束，持续排除其他写入、后台重试和新任务。作者的状态更新请求不携带维护者刚核对的预期占用值，服务只按取得锁时看到的占用更新；如果这段时间可能出现新的生成任务，立即停止。满足条件时经作者正常章节更新入口仅提交已核实的状态。比较操作前后的正文、修订、场景、任务行、取消意图和占用，再重启复读，检查迟到结果、后继任务及意外模型调用。复位只能结论为“章节状态已恢复”；必须另记原任务的实际状态。任一前提或复核失败，丢弃该实验副本、保留原库。双库的真实 0043 冷快照均完成 draft、done 两项复位。四项在独立重启后再观察 3 秒，章节、原任务及清理失败记录均与复位后相符，未增加模型请求。旧排队任务在管理员取消受理 12 秒后及重启观察时仍未收尾。来源不明或有后继占用时，维护者均停止复位。现场缺上述隔离证据时，不能沿用实验结论。[章节矩阵与逐次日志](research/chapter-results.md)

代码依据：[0046 迁移](../../../backend/alembic/versions/0046_chapter_claim_identity.py) 只新增可空占用字段；[作者更新入口](../../../backend/app/services/chapter_service.py) 的 update_chapter 实际调用 [条件复位](../../../backend/app/services/chapter_claim.py)；[管理员取消](../../../backend/app/services/admin_task_service.py) 先登记意图再异步收尾。[编辑器](../../../frontend/src/pages/project/ChapterEditorPage.tsx) 对无法安全关联的任务有专门提示。仓库 README 的一般复位说明不能单独作为旧章可复位的证据。

## 4. 提案处置

**双库已验证的范围。** 对旧版生成的一条内建创建角色提案，分别在升级前取消、升级后取消并发送新消息。原提案的 18 个旧字段从快照直到新版重启均逐项相等，包括参数、预览、效果、原整数轮次和时间戳。确认及拒绝原提案均返回 409，角色数始终为零。新消息只产生自己的模型调用与新任务。迁移新增的提案 UUID 在各自副本内稳定，原轮次键和外部工作者键均保持空值。外部工具是否发生副作用仍须核对外部回执。[提案演练及原始日志](research/proposal-verification.md)

- **已结束或缺原轮次身份。** 保留原行、参数、预览、原任务关系、执行结果与状态。核对记录分别写“原提案仍未决”“效果已核实／未知”以及证据来源。保留 proposed 与页面上的历史提示；不补 turn_task_key、不写成 rejected、不删会话来消除提示。[0047 迁移](../../../backend/alembic/versions/0047_agent_change_identity.py) 为每条提案分配 change_key，但明确不给旧消息／提案回填原轮次键；[确认与拒绝服务](../../../backend/app/services/agent/service.py) 复核权限、提案身份和预览版本，[提案卡片](../../../frontend/src/components/agent/AgentChangeCard.tsx) 对已结束轮次关闭动作。
- **旧版重试的特殊记录。** C8 早期 SQLite API 复核曾经重试后拒绝一条残留提案，新任务成功，该轮在升级前中止。旧提交 4501f18 的 backend/app/services/task_engine/handlers/agent.py（build_job）会把同会话内旧任务的消息和提案一起改绑到重试任务。该操作可改变多条记录并继续运行智能体。最终网页复做仍留下不可操作的提案。不能把早期成功外推为逐条关闭旧提案的通用操作。
- **用户仍需要原意图。** 先确认目标当前状态、原提案可能造成的效果及外部回执。若存在重复执行可能，保留待核对并停止。效果明确且用户仍希望执行时，才由有权限的用户明确新发请求，检查新预览并按正常流程决定。分别记录新旧提案和效果。新任务可以产生调用，不用于清理历史。
- **安全结束人工核对。** 可以在维护记录中注明“保留原提案，本次不执行”，给出证据、核对人和时间；原提案的业务状态仍如实保留。若需要在产品内永久标记人工核对结果，须另行设计权限、审计及展示，本方案不要求更改数据模型。

## 5. 恢复判断

仅在选定恢复点、可接受的数据差异、所有潜在写入方、章节及提案处置都已逐项核对，并按 README 完成恢复验收后再切换流量。允许留存有记录、内容完整且不可误执行的历史提案；执行结果未知、活动任务未排空或章节内容不一致的个案保持待查。当前方案没有为缺身份的旧任务提供强制收尾命令。
