# 媒体文件存储（核心能力）

> 父任务：`11-27-admin-plugin-packages`。决定编号 D1–D15、共同需求 R1–R7 见父任务 `prd.md`。
> 规划深度：本文件现在只定需求与验收；`design.md`、`implement.md` 在轮到本子任务、其依赖已落地时再写，届时重新走一次评审。

## Goal

为图片、视频等大文件提供统一的存储与访问能力，供短剧插件和以后的其他功能使用。它是核心能力，不属于任何插件。

## 依赖

无。先于 `11-27-ai-media-models`、`11-27-short-drama-media`、`11-27-drama-canvas`；可与 `11-27-plugin-framework` 并行。

## Requirements

- M1 两种存储位置（D13）：默认本地目录，单机部署零配置即可用；部署者可改配 S3 兼容的对象存储。上层功能不感知用的是哪一种。
- M2 所有媒体只能通过带登录校验的接口访问，按归属与协作权限判定；不提供无鉴权的静态目录。
- M3 视频支持分段读取，浏览器可以拖动进度播放，不需要先整段下载。
- M4 能为单个文件签发有时限的外部访问地址，供视频厂商拉取参考素材（子任务 3 需要）。
- M5 每个文件有元数据记录：归属用户、所属作品、大小、类型、来源、创建时间；可按用户统计占用。
- M6 清理：业务记录删除时对应文件被删除；作品进回收站时文件保留，彻底删除时一并清除；有兜底机制回收无主文件。
- M7 双实例：对象存储下两个实例天然共享；本地目录下要求两台挂同一个共享卷，未共享时要能被发现并给出明确提示，而不是随机 404。
- M8 现有存在数据库里的图片（作品封面、设定缩略图、小说模板图）保持原样，不迁移。
- M9 README 写清两种存储的部署方法、双实例要求、备份边界。

## Acceptance Criteria

- [ ] 本地目录与对象存储两种配置下，同一组「写入 → 读取 → 分段读取 → 删除」用例都通过。
- [ ] 未登录、非归属且非协作者访问媒体地址被拒绝；查看者可读不可删。
- [ ] 浏览器播放一个大于 50MB 的视频可以直接拖到中段播放。
- [ ] 签发的外部访问地址在有效期内可匿名取到文件，过期后失效。
- [ ] 删除业务记录后文件不再存在；作品彻底删除后其全部媒体文件不再存在；人为制造的无主文件会被兜底清理回收。
- [ ] 双实例 + 对象存储：A 写入的文件 B 立即可读。双实例 + 未共享的本地目录：有明确的诊断提示。
- [ ] 作品封面、设定缩略图的现有行为与测试不变。

## 已核实的现状（代码证据，详见 `11-27-short-drama-plugin/research/reference-media-infra-and-gap.md` B.7、B.10）

- 现有图片都存在数据库二进制列里，规范明确不引入图片目录或数据卷
  （`backend/app/models/entities.py:304`、`backend/app/models/setting_images.py:35`、`backend/app/models/novel_templates.py:53`）。
- 整库备份已有本地与 S3 两种存储实现，`boto3` 已是依赖（`backend/app/services/backups/storage.py:60`、`:347`，`backend/pyproject.toml:27`），
  但它只服务备份文件，不是通用存储。
- 容器只挂了数据库卷和备份目录（`docker-compose.yml:10`、`:64`）。
- 参考项目把文件放在本地 `data/static/` 并直接静态托管，没有访问控制；向视频厂商传参考视频 / 音频时需要公网可达的地址。

## 进入本子任务规划时需再确认

- 对象存储由谁配置：部署者用环境变量，还是管理员在后台填写（整库备份是后者）。
- 是否对每个用户的媒体占用设上限，以及默认值。
- 媒体文件是否进入作品备份与整库备份；不进入时如何提示。
- 本地目录模式下，给厂商的外部访问地址依赖站点公网地址，没有公网地址的部署如何处理。
