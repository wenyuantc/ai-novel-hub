# 慢模型响应头与执行者心跳

2026-11-23 的单文件基线发现，SQLite 主库上的心跳会被慢模型请求挤占，导致健康执行者更换身份。独立存放租约后，同一真实发送场景在 SQLite 和 PostgreSQL 均已通过。

## 修复后验收

SQLite 的任务归属和永久围栏仍在主库，权威心跳移至同目录的 `.leases.sqlite3`，运行期间另用 `.leases.lock` 约束离线恢复。慢请求仍持有原来的主库发送锁。本次使用默认 5 秒心跳、30 秒租约、5 秒余量，以真实 SDK 向本机回环 TCP 服务器发送请求。

- **SQLite。** 两个独立应用共用一份主库。服务器收齐请求后等待 32 秒，直到最后才放行响应头和正文。两个 16 秒窗口内都直接查到两个执行者的持久心跳各自前进。放行前任务处于 running，旧正文仍在。服务器共收到一个请求，完成后正文逐字正确，两个执行者的 UUID 均保持。运行 `cd backend && uv run pytest -q tests/test_task_worker_slow_headers.py`，独立复核为 1 项通过、35.46 秒。
- **PostgreSQL 16.15。** 在本机专用测试库的随机 schema 复跑下文的 TCP 研究脚本，增加参数 `-k tcp_provider`。即时和 32 秒组均成功、正文完整、执行者身份保持。主库心跳的独立写探针在收到响应头前以及收到头但尚未给正文时都成功。2 项通过、56.49 秒。另行复跑 `tests/test_task_worker_lease_postgresql.py::test_open_send_can_renew_and_other_expired_workers_can_be_fenced`，验证发送事务期间可续约、同轮能围栏其他失联登记，1 项通过、11.73 秒。
- **同一条双应用用例的跨库复验。** 下文的 PostgreSQL 研究脚本增加参数 `-k preserve_both_worker_leases`，直接复用上方 SQLite 正式用例。PostgreSQL 真实等待 32 秒期间，两个身份在前后两个 16 秒窗口内均提交了更晚的心跳，最终正文正确且请求次数为 1。1 项通过、42.51 秒。

### 主库提交与独立围栏的顺序

真实章节生成另设三个驱动断点。模型只生成一次，章节、日志及完成收据已经提交，原执行者 A 正通过一个新的主库事务提交任务终态和统计。A 始终持有主库写锁，B 可以在侧库决定围栏，但必须等主库可写才能提交围栏并接管。各组在放行 A 前都从独立连接读到任务仍为 running，主库中的 A 尚未被围栏。

| 放行 A 时的事实 | 主库最终顺序 | 终态行的执行者 |
| --- | --- | --- |
| A 已通过业务身份核验，B 在侧库围栏，A 在物理 COMMIT 前已确认失租 | A 的未提交终态及统计整体回滚，B 按已有章节收据收尾 | B |
| A 已通过业务身份核验并持主库锁，B 在侧库围栏，A 的本地租约仍有效且尚未获知 | A 先提交已获准的主库事务，B 随后落实主库围栏 | A |
| SQLite 工作线程已经收到 A 的真实 COMMIT，这时 B 在侧库围栏且 A 得知失租 | 在途 COMMIT 先完成，B 随后落实主库围栏 | A |

三组均保持一份正确正文、一条成功生成日志、一次模型调用，以及一致的任务和统计终态。早期实现允许第一组继续以 A 身份提交。在实际驱动 COMMIT 前增加本地身份与单调期限核验后，三组在独立复核中全部通过，耗时 5.59 秒。运行 `cd backend && uv run pytest -q tests/test_task_worker_sqlite_commit_order.py`。研究目录的 `sqlite_business_fence_order.py` 复用同一组驱动断点。

## 单文件基线的复现

以下记录保留修复前的实验。脚本始终要求成功、正文正确、身份保持。

从 `backend/` 运行。SQLite 每例新建临时文件，PostgreSQL 每例在专用本机 `ainovel_test` 中创建和删除自己的随机 schema。PostgreSQL 使用与验收记录相同的容器，并将环境变量 `AINOVEL_POSTGRES_TEST_URL` 指向对应映射端口。

```sh

PYTHONPATH=. uv run pytest -c pyproject.toml -p tests.conftest -q -s ../.trellis/tasks/11-20-mp-worker-lease/research/postgresql_slow_provider.py
```

脚本通过 HTTP 接口创建账号、作品、模型绑定及带原稿的章节，再提交生成。沿用服务默认的 300 秒模型请求超时、5 秒心跳、30 秒租约和 5 秒安全余量。命令包含发送钩子对照和独立的本机 TCP 模型服务器对照。每组都要求任务成功、正文逐字等于“完整回复”、执行者身份保持。等待期间另外打开一个会话，对该登记的心跳字段执行等值更新后回滚，100 ms 的探针等待只作用于该连接，正式心跳仍用默认等待。

### 发送钩子对照

追加 `-k "not tcp_provider"` 可单独复跑本组。内存模型提供固定正文。脚本先调用真正的 `_PhysicalDispatchHooks._before_request` 完成授权检查并取得数据库发送锁，在模拟响应头返回前等待 0 秒或 32 秒。

SQLite 快响应组得到 `succeeded / 完整回复 / 身份保持`。32 秒组的探针在 UPDATE 处收到 `SQLITE_BUSY`，正式心跳连续两次报告未确认，定时器于等待开始后 24.24 秒取消执行体，任务最终为 `interrupted / 原稿 / 身份已更换`。本轮命令于 09:58–09:59（东八区）执行，结果为 1 项失败、1 项通过，耗时 27.66 秒。先前独立试跑在等待后 24.52 秒取消，结果一致。25 秒安全线从上一次确认登记或心跳算起，开始等待响应头时已经经过一小段时间。

同一钩子、同一断言的跨库复测结果如下。PostgreSQL 16.15 每组均在独立测试 schema 内执行。慢组确实在已持发送锁时等待了完整 32.00 秒，超过 25 秒本地安全线。探针可执行等值 UPDATE，原执行者正常续约并写入完整正文。

| 数据库 | 即时响应组 | 32 秒组实际等待 | 慢组探针 | 慢组结果 | pytest |
| --- | --- | ---: | --- | --- | --- |
| SQLite | 成功、身份保持 | 24.19 秒后被取消 | SQLITE_BUSY | interrupted，正文保留原稿，身份更换 | 1 失败、1 通过，27.60 秒 |

### 本机 TCP 端到端对照

追加 `-k tcp_provider` 可单独复跑本组。章节由实际 `create_provider` 创建 OpenAI 兼容 SDK，通过回环 TCP 连接发出请求。本机模型服务器读完整个 HTTP 请求体后发出测试信号，由脚本分别决定何时发送响应头和何时发送正文。正常身份下在响应钩子完成后、服务器发送任何正文前再次执行独立写探针。每例确认服务器只收到一条完整请求。

- SQLite 即时组在模型服务器读完请求、尚未发送响应头时得到 SQLITE_BUSY。随后仅放行响应头，继续扣住正文，这时执行者行已可写。最终成功写入“完整回复”。
- SQLite 慢组等待期间收到 SQLITE_BUSY，在服务器读完请求后的 23.90 秒观察到执行者身份已失效。服务器于 32 秒放行响应头，原执行体此前已取消，最后查到 interrupted、正文为“原稿”、执行者身份已更换。即时及慢响应两例共 1 失败、1 通过，39.16 秒。
- PostgreSQL 16.15 的即时组、32 秒慢组均在模型收到请求后以及收到响应头但尚未发送正文时成功执行写探针，两条任务均成功、正文完整、身份保持。2 项通过，49.63 秒。两库的实际 HTTP 实验均未访问外部模型。

## 锁在哪一刻阻止写入

`app/services/ai_dispatch.py` 的 `_lock_sqlite` 对作品执行等值 UPDATE。该语句取得主库写事务。实际 HTTP 每跳的请求钩子进入该事务，`app/ai/providers/dispatch_hooks.py` 的 `_after_headers` 在收到该跳响应头后释放。传输异常或取消时由 `aclose` 兜底释放。此屏障规定了发送与作品策略修改、撤权的先后顺序。慢响应阶段能读取库，其他会话写另一张表也会被挡住。流式正文慢读发生在响应头之后，与本实验覆盖的时间窗不同。

用两个独立 `sqlite3` 连接和两个测试表交叉验证。先设置日志模式，在 A 中执行 `BEGIN` 并读作品行或对其执行等值 UPDATE。B 对执行者行、作品行分别执行 `BEGIN / UPDATE / COMMIT`，等待 100 ms，失败后回滚。四种组合中 A 回滚后，B 写执行者行均成功。

| 日志 | A 已执行 | B 修改心跳 | B 修改作品策略 |
| --- | --- | --- | --- |
| 默认 DELETE | UPDATE | UPDATE 返回 SQLITE_BUSY | UPDATE 返回 SQLITE_BUSY |
| WAL | UPDATE | UPDATE 返回 SQLITE_BUSY | UPDATE 返回 SQLITE_BUSY |
| DELETE | SELECT | COMMIT 返回 SQLITE_BUSY | COMMIT 返回 SQLITE_BUSY |
| WAL | SELECT | 提交成功 | 提交成功 |

因此只切换 WAL 无法释放已占用的写槽。改为共享读锁时，DELETE 下心跳仍无法提交，WAL 下策略撤销可在发送锁释放前提交，改变已有授权顺序。持有主库写锁的进程本身可以证明其他事务此时无法改动归属。在释放前更新自己的心跳还需改变本应回滚的发送事务，而且对同一主库的其他健康执行者无效。延长租约会推迟真正失联后的收尾，按主库 SQLITE_BUSY 豁免自我围栏则无法判明哪些执行者仍存活。

## 独立 SQLite 租约文件的最小约束

下列约束是单文件基线后形成的设计依据。已批准和落实的布局、恢复命令及迁移契约以当前任务设计、运行手册和验收记录为准。

1. **划分权威状态。** 主库保存任务归属、终态、收据及已落实的停止或围栏标记。独立租约库保存当前心跳、不可逆的停止或围栏决定。新领取和业务提交同时依赖主库归属、主库登记以及相同实例代次与 UUID 的有效租约。沿用数据库时间、心跳 5 秒、租约 30 秒、安全余量 5 秒。主库中的心跳镜像如果保留，只作诊断。候选扫描、领取与恢复均不能用滞后的镜像判活。
2. **隔离物理写入。** 租约独占一套独立连接，续约不打开主库事务、不等待主库写锁。两库操作分阶段提交，任何等待主库的步骤都必须先释放租约库事务。发送事务不得通过 ATTACH 或同一 BEGIN IMMEDIATE 抢占两个文件的写槽。这样任一执行者慢等响应头时，其余执行者仍能更新心跳。租约库本身不可访问且已过安全期限时，所有无法续约的执行者仍需按 R7 停止。
3. **登记与接管可重做。** 每次执行使用新的 UUID，先提交租约登记，再提交同一代次的主库登记，两边确认后才可领取。中途退出最多遗留没有任务的租约记录。更新心跳使用比较后更新，确认同代、未停止、未围栏、上一心跳尚未到期。迟到确认只能对应原 UUID。接管先在租约库用与续约互斥的条件提交失联围栏，后在主库给同一身份落实围栏，两步均可按身份重试。确认丢失时先回读相应文件里的准确身份。接管者只有确认主库围栏并通过原任务归属比较后才可转移，原有收据与业务恢复继续在同一主库事务完成。任何阶段退出，后续执行者均能从已提交的单向状态续做。
4. **明确在途写的先后。** 旧执行者业务事务先取得主库所有者或任务锁，再检查独立租约状态，通过后持续持有主库锁直至提交。已获准的该次写在线性顺序上先于主库围栏。接管者须等待该事务释放后才能在主库改归属。独立租约失效后禁止旧身份开启新的授权写或发送，入口和业务提交边界均须校验本地截止时间。执行体因自我围栏取消时回滚未提交事务。慢模型等待期间仅保持发送屏障，正文写入在单独事务重新校验。候选扫描遇到部分落实的围栏时须继续传播。主库已围栏的身份永远不能因旧心跳回复或另一侧登记恢复而复活。
5. **识别实例与存储丢失。** 租约文件与主库同挂载、同一部署约定路径，使用持久实例代次关联两者。规范化相对路径与符号链接，防止一份主库对应两份活跃租约文件。启动时在跨进程互斥下初始化。已有主库与登记的启动、续约须验证代次和文件身份，防止路径被删除后旧进程继续写原文件句柄。文件缺失、损坏、代次不符或被替换时，禁止自动建空库并批量认定原登记死亡，也禁止旧进程延用旧身份。运维冷恢复须先确认所有旧进程退出，持久切换新代次，再按旧运行中任务的恢复规则收尾。内存 SQLite 及每个测试进程使用的临时库也要显式定义配对方式。
6. **备份与时间上限。** 原生备份需成对取一致快照，或明确单主库快照恢复时执行冷启动代次切换。作品 JSON 备份保持作品范围。租约文件正常时，主库长写锁期间健康进程仍可续约、失联决定可在租约库落地。如果主库写锁连续超过 35 秒，即使已确定旧进程失联，也无法在主库提交任务收尾。需明确 R6 对主库可写的前提、释放锁后的立即或有界重试，并用独立测试给出证据。

完整验收还涉及多进程中旧进程死亡后的接管、登记与围栏各阶段崩溃、提交确认丢失、文件缺失或替换、冷备份恢复、迟到心跳及旧业务写。跨进程长持锁及强杀的实测数据另见同目录 `sqlite-contention.md`，逐项验收汇总见 `verification.md`。
