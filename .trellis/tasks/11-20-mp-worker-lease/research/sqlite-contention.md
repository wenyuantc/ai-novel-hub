# SQLite 双进程争用基线与正式租约复测

2026-11-23，在同一台机器上用两个独立 Python 进程共享一个临时 SQLite 文件。两个进程各运行一个实际的 `TaskEngine`、各有自己的连接池、授权运行时和调度循环。本轮 32 个任务全部成功，二者各领取 16 个，每条任务只进入执行体一次，32 份最终正文逐字相符。正常负载期间，驱动错误计数为 0。

## 工作负载与复跑

从项目根目录执行：

```bash
cd backend
PYTHONPATH=. uv run python ../.trellis/tasks/11-20-mp-worker-lease/research/sqlite_contention.py --tasks 32 --control
```

- 环境为 Python 3.12.10、SQLite 3.47.1。生产连接工厂实际读回的 `PRAGMA journal_mode` 为 `delete`，`PRAGMA busy_timeout` 为 5000 ms。
- 使用 `spawn` 独立创建进程和数据库连接。两端都启动后，同批插入测试队列，同时开始调度，每进程最多并发 2 条任务。每条任务以 100 ms 的间隔发出 24 个片段，每片 64 字。真实引擎执行队列领取、每个片段的身份门禁、按默认 2 秒节流的正文刷库和终态事务。合成 handler 提供固定正文，不访问模型或网络。
- 本轮在 0065 基线上运行。基线尚无 `task_workers`，使用每进程一行、每 5 秒一次的独立短事务模拟心跳更新。这组数据验证 SQLite 写竞争，不验证正式心跳的身份约束或接管行为。
- 第 7.3 步在同一命令末尾加上 `--require-lease`。此模式要求模型带有 `task_workers`、两个进程都实际更新正式心跳并刷库、没有驱动错误，且每个任务恰好执行一次。脚本只在 `TemporaryDirectory` 创建库，退出后自动清除。
- `--control` 在正常负载结束后单独校准超时。A 持有已执行 UPDATE 的事务，B 在另一条连接修改同一行，B 收到超时后 A 才释放写锁。随后 B 用新事务重做并要求成功。这个故意制造的锁竞争与正常工作负载的错误计数各自报告。

## C1 参数与边界

1. 维持当前回滚日志及驱动默认 5 秒等待。本批次正常写入耗时均低于该阈值。保留已有授权、发送与内容屏障的局部限时策略。
2. 心跳保持 5 秒一次，租约 30 秒，安全余量 5 秒。心跳或接管的幂等事务遭遇数据库忙时，回滚并释放连接，在下一次心跳或调度时用新事务重新评估条件。单周期内不循环重试。持续无法续约达到本地 25 秒安全期限时停止领取、按设计处理失去租约。5 秒等待包含在安全期限内，记录成功的时间必须能抵御阻塞与提交延迟。
3. C1 的新增写入位于后台引擎。把暂时的数据库忙留在心跳与调度循环内处理，仅记录安全诊断。此负载未观察到需要新增全局 HTTP 异常映射的证据。SQLITE_BUSY 的控制组说明了长事务仍可导致超时，正式实现需保持事务短小、避免同一轮中叠加多次驱动超时。
4. 此次测量覆盖同机双进程、短事务与无网络的流式任务。主库心跳方案的成功样本只适用于该实现。真实慢模型发送持写锁期间的误围栏见同目录 `sqlite-slow-provider.md`，独立租约文件的 AC9 复验结果见下文。

## 独立租约文件的验证方法

短事务压力用 `--require-lease` 复跑。在 `WorkerLease.heartbeat()` 返回成功后单独计时，另开只读连接核实租约文件中当前 UUID 的心跳和标记。结束时验证权威心跳已前进、两端已正常停止且没有围栏，并从主库核对相同 UUID 的停止标记。主库各阶段的写语句分布与租约库的续约整段耗时分开报告。

长事务与真实失联使用第二个脚本。从 `backend` 执行：

```bash
PYTHONPATH=. uv run python ../.trellis/tasks/11-20-mp-worker-lease/research/sqlite_lease_processes.py
```

该脚本让两个真实进程各领取一条任务。B 将主库写事务保持超过一个租约期，协调进程直接观察 A、B 的权威心跳是否持续推进。随后协调进程只对本次测试创建的 A 发 SIGKILL，B 继续持主库锁。侧库确认 A 失联时主库应仍保留原归属。释放写锁后，B 要求自己的任务完成、对 A 只做一次中断清理、两条终态与统计相符。默认使用引擎的生产参数，`--fast` 用于开发时缩短等待。

### 真实强杀与长写事务

两次独立运行均退出 0。默认配置使用 30 秒租约、5 秒心跳和 5 秒调度。生产参数下 B 在主库保持同一写事务 64.99 秒。前 35.11 秒两个任务一直归各自执行者，两条租约从外部只读连接各观察到 7 次心跳前进。向 A 发 SIGKILL 后 29.87 秒，外部连接读到权威租约已经围栏；此时 B 仍握主库写锁，A 的主库运行状态和归属保持原值。放锁后 0.08 秒以内，B 的事务成功、B 的任务成功、A 的任务和统计均变为 interrupted。B 对 A 仅调用一次中断清理，最后自身正常停止，未遭围栏。

| 配置（租约 / 心跳 / 调度） | A / B PID | 强杀前持锁 | A / B 心跳推进 | 强杀至侧库围栏 | 总持锁 | 放锁至两条终态与统计一致 |
| --- | --- | ---: | --- | ---: | ---: | ---: |
| 30 / 5 / 5 秒 | 83957 / 84127 | 35.11 秒 | 7 / 7 | 29.87 秒 | 64.99 秒 | 0.08 秒 |
| 6 / 1 / 1 秒 | 83956 / 84126 | 7.03 秒 | 7 / 7 | 6.65 秒 | 13.69 秒 | 0.14 秒 |

计时起点依次为拿到主库写锁、发送 SIGKILL、协调进程通知放锁。结束以外部读到实际持久状态为准。这项演练使用合成 handler 持有真实业务写事务；实际模型响应头等待与撤权的验证另见慢响应测试。
