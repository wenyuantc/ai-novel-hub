# 多进程任务调度：总体技术设计

> 父任务的跨子任务设计。各子任务在自己的 `design.md` 中细化并可在研究后修正；与本文件冲突的修正须回写到这里。需求见 `prd.md`。

## 1. 设计原则

1. **数据库是唯一的跨进程事实来源。** 任何「某任务是否有人在执行」的判断都来自数据库中的执行者登记，不来自本进程内存。本进程内存只用于判断「是不是我在执行」。
2. **执行进程是活动任务的唯一权威。** 运行中任务的取消、实时帧、输出核验都由执行进程完成。其他进程对活动任务只做两件事：把请求转交给执行进程，或按库内事实等待结果。
3. **接管必须先围栏再动手。** 只有通过条件更新赢得接管权的进程才能对失联任务做收尾；被接管的执行者此后的任何写入都因条件不符而失败关闭。现有的 `execution_key` 逐事件核验（`execution_identity.matches_running` / `require_write_execution`）继续作为任务级围栏值。
4. **轮询保证正确，内部通道只做加速和保真。** 所有跨进程协作在只有数据库轮询时也必须正确收敛；内部通道不可达只影响延迟和流的粒度。
5. **两种数据库同一套逻辑。** 不使用 `LISTEN/NOTIFY`、advisory lock 等只在 PostgreSQL 有的机制承担正确性；共用业务归属与认领条件；方言差异集中在执行者存储、取锁与时间表达式中。
6. **单进程兼容。** C1 的失联恢复时延见第 2.5 节。C2 统一领取提交前后的配额和排队显示，见第 3 节。

## 2. 执行者登记与租约（C1）

### 2.1 数据结构

新表 `task_workers`，每个应用进程在引擎启动时登记一行：

| 列 | 说明 |
|---|---|
| `worker_key` String(36) 主键 | 进程每次启动生成的 UUID |
| `started_at`、`heartbeat_at` | 数据库时间 |
| `stopped_at` 可空 | 正常停止时写入 |
| `fenced_at` 可空 | 被其他进程判定失联并围栏时写入 |
| `hostname`、`pid` | 仅用于诊断与管理端展示，不参与正确性判断 |
| `peer_url` 可空 | 内部通道地址，C4 使用 |

`tasks` 新增两列，均为普通可空列，不建外键（SQLite 上给 `tasks` 加外键需要重建父表，会触发既有生成日志与智能体外键的副作用，见 `.trellis/spec/backend/admin-dashboard.md:105`）：

- `worker_key`：领取时与 `status='running'`、`execution_key` 同一条条件 UPDATE 写入。它同时是进程级围栏值：执行身份核验在比对 `execution_key` 之外增加比对 `worker_key`，任务被其他进程认领后，原执行体的写入即失败关闭。
- `recovered_at`：恢复逻辑决定「保留 running 待核对」时写入，表示这条 running 已由恢复处理过、当前无人执行。它取代进程内的 `_uncertain_executions`，使「结果待核对」在任一进程一致。重新领取时清空。

SQLite 主库的 `task_lease_store` 保存文件配对。每个主库旁的 `.leases.sqlite3` 记录权威心跳，`.leases.lock` 在引擎运行期间持有共享读锁，供离线冷恢复或降级核验。主库 `task_workers` 保存任务归属所需的登记及已传播的停止或失联决定。PostgreSQL 直接使用 `task_workers`。

### 2.2 存活判定

- 存活：`stopped_at IS NULL AND fenced_at IS NULL AND heartbeat_at` 在租约期限内。比较一律使用数据库时钟（同一事务内读取数据库当前时间），不使用各进程的本地时钟。
- 参数为引擎类属性，可由部署配置覆盖，测试中缩短：心跳间隔 5 秒，租约期限 30 秒。
- 心跳协程在对应存储的短事务中只更新仍在有效期内、尚未停止或围栏的登记。影响零行后旧身份退出。SQLite 执行者即使持主库写锁等待模型响应头，仍能在侧库续约。
- **自我围栏**：进程用单调时钟记录上次已确认的心跳请求发起时刻。心跳返回 0 行，或距上次成功已超过「租约期限 − 安全余量」，进程即认定自己失去租约：停止领取，取消本进程全部执行体（它们的收尾写入会因任务已被接管而条件不符，不产生写入），清空内存登记，然后以新的 `worker_key` 重新登记。
- 领取事务内核对本进程的登记行仍然有效，已被围栏的进程不能再领取。
- 正常停止：`stop()` 在本进程任务全部收尾后写 `stopped_at`。其他进程不必等租约到期。

### 2.3 孤立任务的唯一定义

```
status = 'running' AND recovered_at IS NULL
AND (worker_key IS NULL OR worker_key 指向的执行者不存活)
```

`worker_key IS NULL` 的 running 行来自升级前的旧版本。按 D5，升级时旧进程已全部停止，这些行视为孤立，与现有行为一致。

C1 的启动及周期恢复统一调用 `workers.prepare_orphan_scan(db, seconds)`。SQLite 在侧库原子确认停止或失联后将该决定同步给主库。单看主库心跳、或只看到侧库缺某条记录，均不足以接管有归属的任务。取消、管理员排空和作品删除在 C3 接入此入口。

### 2.4 接管协议

由每个存活进程的调度循环周期执行，启动时的 `recover()` 是它的一次立即执行：

1. **围栏失联执行者**：对租约已过期但尚未围栏的登记行做条件更新写入 `fenced_at`。条件包含「心跳仍然过期」，与该执行者的心跳更新在同一行上互斥。
2. **逐任务认领**：对每条孤立任务做条件更新，把 `worker_key` 从原值（或 NULL）改为接管进程自己的值，条件包含 `status='running'`、原 `execution_key`、原 `worker_key`。影响行数为 1 的进程才继续；其余进程跳过。认领后该任务在接管进程内登记为「恢复中」，不算执行体。
3. **按业务凭据收尾**：根据分析、向导、单章、批量的完成收据结束任务，富文档提案转待审核；无法证明的写 `recovered_at` 并清空 `worker_key` 后保留 running。其余任务清理各自资源并记为中断，单章和向导的事务约束见下一项。
4. 接管者也可能中途失联。单章释放占用会消耗任务内的原凭据，向导清理会删除唯一的未提交证明。C1 将这两条恢复路径的资源清理、终态和统计合并到同一事务，其他路径按各自的幂等条件重入。每个写事务核对当前归属。接管进程退出后，由下个进程在其租约到期后继续；仍存活的接管进程按原归属重试暂时失败的收尾。

C1 在启动及每次定时接管时检查已超过 2 分钟阈值的外部调用，同时核对调用身份与本地在途记录。C3 在 0068 中绑定实际发起 worker，保留仍在途的健康调用。

### 2.5 可见的行为变化

单进程崩溃后立即重启时，旧登记行的租约尚未到期，遗留任务不会在启动瞬间被标为中断，而是在租约到期后（默认至多约 35 秒）由周期接管处理。正常停止后可立即识别已停止的登记。若 SQLite 主库被健康进程长时间持锁，侧库先确认失联，主库恢复可写后才提交任务收尾。

## 3. 调度约束改为数据库事实（C2）

领取事务已经持有全局门（`authz.gate`，对 `authorization_state` 单行的更新），所有进程的领取在这一点上串行。在门内追加判定：

- **全局、用户和串行键占用**由原执行轮次的持久记录决定。正常领取在同一事务登记，原执行体完成回调、清理和发布后按轮次归还。确认原 worker 停止或失联也可回收。C1 的恢复接管及待核对任务本身均不新占名额。
- **同键顺序**按符合队列条件的最小任务 ID 决定。队首缺少用户额度或处于本地退避时，后项仍须等待。
- **显示时点**以数据库提交为界。领取提交后，两端均显示占用，即使执行方尚未收到回执。提交前，排队位次仍包含已被本地预选的任务。其余占用细节见 [C2 设计](../archive/2026-11/11-20-mp-scheduling-constraints/design.md)。
- 调度扫描仍是每个进程全量读排队任务；多进程下只是多做无效尝试，由门内判定保证正确。

系统设置：

- **安全开关读库判定**：注册开关在注册入口读库；MCP 总开关在插件管理、刷新工具、试用调用处改用与智能体真实发送相同的读库门禁（`mcp/settings_gate.py`）。
- **其余键有界收敛**。每个应用实例独立定时核对 `system_settings` 的 revision，变化时在发布临界段内重载。存储正常时，一个调度周期内生效。领取在原事务内读取最新有效上限。
- 配额页的「已用并发」改为读库。
- `settings_confirmed` 仍是各进程自己的故障保护；其他进程经 revision 比对收敛到库内事实。

## 4. 跨进程取消与排空（C3）

- 本人取消按原任务、轮次和执行 UUID 持久登记；执行端最多一个调度周期发现。已完成业务提交时保留真实赢家，失联时先经 C1 接管。本机与对端在同一现有等待窗口内返回原任务状态。
- 管理员维持 202 受理和一次审计。运行中由执行者或成功接管者处理；排队、待审核及恢复清理在第一次业务动作前争同轮唯一的处理权。业务收据裁定终态和可重试步骤。
- C2 的并发名额可早于原协程退出归还。作品级任务在领取事务内登记作品、轮次和执行者，原协程退出后确认。请求侧清理、失败收据和未决外部调用也参与作品删除的最终复核。请求执行者的登记覆盖 HTTP 生命周期，停止调度仍能处理请求。
- 删除意图绑定发起者及 token。其他实例的启动和周期恢复只解除已可靠确认停止的原意图。外部调用登记真正的发起者；健康慢调用可完成，接管保留未知结果，不重发。
- C3 的详细收据、历史数据处置及验收见[子任务设计](../archive/2026-11/11-20-mp-cross-process-cancel/design.md)。C4 再增加跨进程即时唤醒。

## 5. 进程间内部通道与实时流转发（C4）

### 5.1 通道

- 每个进程在 lifespan 中启动一个只供内部使用的监听，并把地址写入自己的 `task_workers.peer_url`：同机多进程使用本机套接字文件（权限仅属主）；多实例使用实例内网地址加端口，由部署配置给出对外通告的主机名。
- 内部请求用从 `JWT_SECRET` 域分离派生的密钥做带时间戳与随机数的签名，接收方校验后才处理。内部路由不挂在对外的路由表上。
- 通道承载：流转发，以及取消、唤醒调度、协作成员变更、设置重载这几类「只带标识、不带内容」的唤醒。唤醒丢失不影响正确性。

### 5.2 流转发

- 订阅路由先按库判定执行者。是本进程则走现有管线，不变。是其他存活进程则向其内部通道发起同一订阅，并把帧转给客户端。
- **协作者受控流的两段核验**：执行进程按现有受控管线逐帧核验来源证明与读者授权后发出帧；转发进程在把每一帧写给客户端时，再持有一次本进程的帧发送租约并按订阅原绑定复核读者授权（现有 `_task_frame_lease` 中依赖数据库锁的部分）。这样「撤权提交后没有后续帧到达客户端」的性质在多一跳后仍然成立。来源证明仍只在执行进程内成立，转发进程以「帧来自已鉴权的执行进程、且属于本订阅」作为来源依据。详见[两端授权复核](../archive/2026-11/11-20-mp-peer-channel-stream/research/guard-implementation-review.md)。
- **降级路径**：执行者不存活、通道不可达或转发中断时，转发进程改为按库内值跟随：定期读任务行，文本或进度变化时发快照，任务结束时发与持久回放相同的终止帧。作者可以跟随持久快照直到结束。协作者可以回放经核验的暂停或终态。运行中的正文缺少活动来源证明时，客户端收到受控错误，恢复连接后重新订阅。
- 非执行进程不再为他进程的活动任务创建本地 hub，已有的残留 hub 在读路径上不再被采信：`/output`、`TaskOut` 的进度覆盖、管理监控只在「本进程是执行者」时读 hub，否则读库。

## 6. 引擎外状态（C5）

| 项 | 方向 |
|---|---|
| 备份执行领取 | 改为条件更新，只有一个进程领到 |
| 备份启动恢复 | 只处理发起进程不存活的活动备份，需要在备份记录上记录执行进程 |
| 本地备份目录 | 要求多主机共享；下载时文件不在本机且记录显示由其他主机写入时返回明确错误，不标缺失 |
| 灵感生成锁 | 换成数据库层互斥，保存轮次带版本条件 |
| 项目导入两步 | 数据库加密暂存原始上传分块，使用全站配额及有效期，确认与创建作品一起消费令牌 |
| 智能体会话锁 | 数据库保存会话操作归属，覆盖 SQLite 和 PostgreSQL。跨提交保留会话占用及外部调用收据 |
| 回收站清理、仪表盘采样、用量收尾、备份计划受理 | 已有数据库层兜底，只降低重复尝试产生的错误日志 |
| CPU 并发限流器 | 保持每进程各自限流，写入文档 |

## 7. 排空开关（C6）

- 新增系统设置项，表示「停止受理新任务」。
- 判定点在任务受理的统一入口（创建、继续、重试），在受理事务内读库，保证任一进程下一次受理即生效。
- 运行中任务派生的后续任务（如成功后的自动分析）属于在途工作的一部分，是否放行在 C6 的需求中确定；默认放行，使在途流程能完整结束。
- 管理端系统设置页增加开关，并展示剩余活动任务数（排队、运行中、待审核）与存活进程列表（来自 `task_workers`）。
- 被拒时返回固定提示与受控错误码，前端沿用现有错误展示。

## 8. SQLite 多进程

- 只支持同机多进程共享同一数据库文件。
- 所有新增机制都不依赖行锁；需要互斥的地方用「条件更新 + 影响行数」，在 SQLite 上由文件级写锁保证。
- 保持回滚日志模式（现有受控流的共享读租约依赖它，`stream_lease.py:204-224`）。
- 多进程写入争用靠 busy 等待排队。C1 先实测两个进程的并发领取、独立租约心跳及正文刷库，保留 SQLite 默认 5 秒忙等待。后台接管遇忙回滚，下一轮按同一永久围栏继续，用户请求仍依照各业务已有的错误处理。
- 心跳与取消请求扫描带来的额外读写在 C1 中量化，必要时在 SQLite 上放宽间隔。

## 9. 迁移、部署与兼容（C7）

- **迁移并发保护**：`alembic/env.py` 在检查版本前取得跨进程互斥。PostgreSQL 在同一数据库会话持有 advisory lock，这里只保护迁移这一运维动作，不承担运行期正确性；SQLite 在迁移专用连接关闭外键后显式使用 `BEGIN IMMEDIATE`，将版本检查、结构变更和版本更新纳入同一受控事务。迁移完成前核验外键，异常回滚；不得用历史迁移中的自动提交块提前释放保护。后到者重新检查版本，已是目标版本即无需再迁移。[C7 设计](../archive/2026-11/11-20-mp-deploy-acceptance/design.md) · [迁移预研](../archive/2026-11/11-20-mp-deploy-acceptance/research/migration-research.md)
- **新增迁移**（编号在各子任务中按当时 head 顺延）：`task_workers`、SQLite 的配对表 `task_lease_store` 与 `tasks.worker_key`／`recovered_at`（C1，0066）；`task_work_records`、`tasks.cancel_requested_at`、删除与外部调用的发起 worker（C3，0068）；备份执行进程标记与灵感互斥所需列（C5）；排空开关（C6）。降级遵循现有惯例：存在新语义数据时拒绝。
- **升级到含租约的版本仍需停机**（D5）。旧版本遗留的 running 行没有 `worker_key`，按孤立处理。
- **启动方式**：镜像默认仍是单进程；通过环境变量选择 worker 数。多实例部署的内部通道地址、共享 `BACKUP_DIR`、相同的 `JWT_SECRET` 与 `ENCRYPTION_KEY` 写入 README。
- **文档与规范**：README「当前限制」与第 96 行的单进程警告改写；`.trellis/spec/backend/` 中所有写明单进程前提的规范同步更新（`database-guidelines.md`、`error-handling.md`、`admin-task-monitoring.md`、`rbac-quotas.md`、`system-settings.md`、`recycle-bin.md`、`inspiration.md`、`project-transfer.md`、`admin-dashboard.md`、`skills-mcp.md`、`directory-structure.md`、`admin-backups.md`）。各子任务更新自己触及的规范，C7 做最终一致性检查。

## 10. 测试策略

三层，逐层收敛：

1. **同进程双引擎测试**（默认 SQLite，随 CI 运行）：新增夹具在同一个数据库上构造第二个应用与引擎，用来验证领取互斥、租约、接管、调度约束、取消请求。它验证数据库层协议，不验证进程隔离。
2. **PostgreSQL 用例**（`AINOVEL_POSTGRES_TEST_URL` 手动启用，串行）：对行锁语义与并发敏感的协议各补一组，沿用现存三个文件的守卫与随机 schema 方式。
3. **真实多进程验收**（C7）：脚本启动多个真实应用进程与本地假模型，分别接 PostgreSQL 16 容器和 SQLite 文件，按 `prd.md` 的 AC1–AC11 逐条执行，包含强杀进程、断开内部通道等故障注入。脚手架参考 `.trellis/tasks/archive/2026-11/11-18-browser-acceptance-backlog/research/harness/`。

## 11. 风险与待研究

| 风险 | 说明 | 处置 |
|---|---|---|
| 接管与「僵尸执行体」并发 | 被围栏的进程在得知之前仍可能处于保存事务中；`on_abort` 与它交错时的资源结果此前未核实 | C1 研究逐个 handler 推演并用双引擎测试固定；原则是双方都在同一组数据库锁内以条件更新决胜 |
| 受控流多一跳后的零泄露 | 转发引入帧在途窗口 | 第 5.2 节的两段核验；C4 先研究、独立复核 |
| SQLite 写争用 | 多进程下心跳、刷库、领取互相等待 | C1 实测定参；C7 在 SQLite 上完整验收 |
| 心跳被事件循环阻塞 | 长时间同步计算会让存活进程被误判失联 | 自我围栏保证安全性（误判只导致任务被中断，不产生双写）；C1 排查引擎路径上的同步重计算 |
| 内部通道的部署复杂度 | 多实例需内网互通与正确通告地址 | 降级路径保证不可达时功能可用；C7 文档与验收覆盖 |
| 进程内屏障的持久化范围 | `_abort_failures`、`_cleanup_work`、`winners` 等原本随进程存在 | C3 研究逐项决定持久化或以保守失败替代，不追求全部持久化 |
| 测试改写量 | 约 100 个测试文件调用 `engine.start()/stop()` | 保持夹具与默认行为兼容；只改写直接断言内存计数的用例 |
| 时间表达式的方言差异 | 租约比较要在 SQL 条件内完成 | 封装为一个助手，两种方言各有测试 |
