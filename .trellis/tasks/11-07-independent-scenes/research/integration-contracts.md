## 2. 最小数据与写入边界

- 场景正文为唯一实时事实；Chapter.content 只是同事务维护的兼容投影，继续供阅读、导出、开放读取、前章上下文和旧提及协议消费。
- 使用一个章级内容／结构 revision 保护同章所有场景，而不是同时引入互相独立、难以证明一致的章与场景正文版本。
- 新增稳定场景身份，保留已移出当前结构的场景身份供历史和锚点判断。普通删除不靠复用 ID；物理级联删章后仍不凭编号认领旧事件。
- 场景规划复用 PlanningUnit 及现有类型化关联，新增 scene 来源和本地角色关联；覆盖模式按 POV、标签及五种关联分别表达，继承不复制有效值。
- 场景排序／拆并、正文保存、兼容章投影、字数和结构版本由同一事务编排层维护；下层原语只 flush，不自行 commit。

## 3. 无损正文分隔

仅用固定空行 join 无法同时保证“新场景自然分隔”和“任意光标拆分不改原文”。采用场景前缀分隔信息：

- 初始场景无前缀；新插入场景默认普通空行分隔。
- 拆分按原始码点切片，新右片不额外加字；合并包含原分隔。
- 结构快照保存分隔信息；更换首场景不丢弃文字。维护原文字符与结构显示分隔的区别，不能通过 trim 掩盖不一致。
- 用户不需要编辑内部格式；服务端是唯一拼接者，前端只消费服务端投影和偏移。

## 4. 旧时间位置的兼容扩展

保留旧章级边界，在它们之间插入真实场景序列：

~~~text
章号 N 的旧 start
  → 同号实际章节按既有 (chapter_no, chapter_id) 展示次序
    → 各章场景 start/end（按当前稳定场景顺序）
  → 章号 N 的旧 end
~~~

- 旧 planned/chapter 事件仍只使用章号和旧边界，其相互排序不变；同号章不被迁移重新编号。
- 新 scene 事件解析真实 Scene ID、所属章和当前顺序；请求不能自报排序号作为事实。旧 API 的纯章初／章末预览继续保持旧含义。
- 同号章节下，旧章级事件仍属于共享章号窗口，而不是追认某个新场景。新 UI 明示这个兼容边界；场景事件可以精确指向实际场景。
- 场景开始使用截至 start 的值；本场景 end 事件不提前进入本场景生成。场景排序后重验完整历史，不合法则整体拒绝。

## 5. 拆并和恢复的安全可实现范围

- 排序只改稳定身份的位置。拆分原始文本可无损切片，但已有场景专属演变／支线／交汇时需先处理无法证明归属的引用，不能假设都属于左片或右片。
- 合并时，位于两场景中间的演变边界无法用合并后仅有的 start/end 等价表示；这类保留事件阻止合并，作者须先显式重绑或处理。冲突元数据需明确选择。
- 首版不做字符级时间锚点，也不为“自动让合并成功”增加隐藏子场景。严格拒绝冲突符合已确认 D5。
- 结构历史恢复只恢复章节场景结构、场景正文／摘要和本地覆盖；章默认、独立支线节点／交汇和设定演变不是正文版本的回滚对象。若恢复会使这些资料失联，先阻止并提示处理。
- 退场场景身份仍保留；显式恢复旧结构须校验所属章、来源绑定代次和当前引用，不能自动抢回已被作者改挂的规划单元。

## 6. AI 的有界迁移方式

- 复用 chapter.generate/polish/revise 任务类型与章资源键，request 增加经过严格解码的目标描述；旧 request 缺目标时按整章解释。不为场景发明新的权限动作或绕过旧任务生命周期。
- 单场景入口只是明确目标；整章入口依次处理当前目标场景，并暂存正文提案，所有目标主生成成功后一次性提交。原任务重试仍重新核验当前资料；不自动接纳旧场景半成品。
- 整章批量仍按章 checkpoint。已完成前章保留；当前章主生成失败／取消不部分覆盖。自动续写 warning 与主生成失败分开。
- 统一场景上下文解析器向提示词、选角、设定投影和预览传递相同目标。可见策略继续走现有 guard_provider；追加场景／规划／时间线快照校验，不跨网络调用持数据库写事务。
- 优先复用现有模板 key 和锁定变量补齐模式；新增锁定场景范围块，旧覆盖漏变量仍兜底一次。默认模板明确仅写当前场景，不能因复用 key 继续要求每个场景完成整章。
- 本期不新增场景自动分析流水线。既有章级自动分析／记忆仍在整章成功后按章末运行；独立场景写作导致旧章分析过期，需要提示重新分析，不自动把局部结果冒充完整章末事实。场景演变由明确场景锚点维护。

## 7. 对测试与实施路径的影响

- 生产升级会回填初始场景；create_all 和直接 ORM 测试种子不会跑生产回填。必须明确适配真实需要场景的 fixture／seed，不能用 GET 隐式修复写库来迁就旧测试。
- 必须测试真实 Alembic 0038→0039 和 fresh 全链、SQLite 及真实 PostgreSQL，而不是只跑新 ORM create_all。
- 新 PostgreSQL 验证采用专用本机测试库和 UUID 隔离 schema；参考 tests/test_series_postgresql.py，禁止复用生产／开发库。环境不可用时如实记录未验，不用 SQLite 冒充。
- 多个模块是一项不可分割的发布切换：统一场景化会改变所有正文写入口，基础层单独发布会造成旧写入覆盖。保留单个任务，按有序责任切片执行与验收，不建立看似可独立交付却不安全发布的子任务。
