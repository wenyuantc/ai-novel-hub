# 账号与本机插件联合验收

2026-11-26 在从 0076 迁移至 0079 的隔离 PostgreSQL 16 库运行两个独立 Uvicorn 进程。部署清单登记仓库示例 `backend/examples/manuscript_stats_mcp.py`，两台服务使用同一目录版本和固定命令。HTTP 请求直接进入现有前后端共用的公共 API，实际启动 stdio 进程。Linux DO 和 GitHub 的外部令牌交换与身份查询使用测试适配器；本地的授权状态、回调、数据库绑定、登录挑战和 Cookie 均走产品实现。

| 交叉场景 | 观测结果 |
| --- | --- |
| 账号与私人插件 | 原作者 ID 1 创建书稿 ID 2，启用目录项 `mystats` 得到私人插件 ID 1，重复启用仍为同一记录。在两个独立客户端分别经 Linux DO、GitHub 回调，第二步之前读取书和私人插件均为 401；分别用两枚恢复码后，两种入口都取得原用户 ID 1、原书 ID 2 和原私人插件 ID 1。 |
| 第二作者 | 独立登录用户不能读取作者的书及私人插件。该用户从同一部署目录启用插件得到自己的私人记录。 |
| 编辑协作者 | 另一独立用户接受该书的编辑邀请后可以读取作品，读取作者私人插件仍返回 404。其协作智能体会话即使提交自己的插件 ID 也收到 403，错误码为 `collaborator_mcp_unavailable`。 |
| 全站开关与多进程 | 原作者通过 A 刷新工具清单，通过 B 试用真实 `count_characters`，输入 `ab cd` 返回 `4`。A 的后台保存关闭全站 MCP 后，B 对已登记 stdio 插件以及该作者独立的远程插件调用均返回 403。恢复原设置后结束测试。 |
| 升级与兼容 | SQLite 和 PostgreSQL 均已完成 0076 → 0077 → 0078 → 0079 升级。旧用户 ID 1 在两库均保留密码登录能力。另在 SQLite 副本删除 ID 900 的最后一条远程插件后升级 0079，再建远程记录得到 ID 901，验证已删除记录的自增高水位得以保留。 |

两家第三方平台的真实账户授权和外部服务回包仍待测试应用验收。此处远程插件验证全站关闭时的拒绝行为；本机示例的真实进程通过标准输入输出完成了调用。登录页面、密码／两步登录、人工恢复审计的独立证据见[登录子任务验收](../../11-26-oauth-two-step-login/research/verification.md)。
