# 站内通知实施计划

本任务交付一个收件箱。以下步骤按依赖排序，当前阶段为规划，所有勾选项均指后续实施工作。

| 步骤 | 实施内容 | 本步验收 |
| --- | --- | --- |
| 1. 打通一条邀请 | 建收件、偏好及事件唯一约束，完成迁移。接入作品及系列邀请的事务，打通列表、未读数、已读、偏好和目标解析 API。 | A1、A5。两个账号对同一邀请的查询结果不同，重复提交及回滚均符合预期。 |
| 2. 接入任务和检查 | 盘点终态写入点，覆盖普通收尾、手工完成和恢复。建立检查成功的独立分支，加入按运行 ID 读取历史概要的接口，并给去重后的两位接收人分别投递。 | A2、A3。验证普通任务成功和失败、失败后重试、两次检查的准确定位、作者与发起人的偏好和已读隔离。 |
| 3. 接入预算 | 复用现有费用查询的汇总规则，初始化已有预算的基线。在结算时判断账号月度和作品累计预算，处理阈值重合、变更、跨月及并发。 | A4。覆盖两笔费用合计越线、相同结算重放、月底调用次月结算、预算移除重设及作者代付。 |
| 4. 接入工作台 | 在桌面和移动布局加入入口、未读数、列表和开关。为书架邀请、个人任务、预算币种、检查运行提供可复验的定位；前台刷新与身份切换使用同一套失效机制。 | A1–A7。逐条点击四类真实通知，打开正确业务对象。空列表、零未读、失效目标、网络失败能区分并可恢复。 |
| 5. 验证并同步文档 | 对四条来源跑撤权、分页、去重及迟到响应测试。更新相关跨层规范、README 和 TODO #27，并记录执行结果。 | 四类端到端均通过后再勾选 TODO。 |

## 回归重点

- **账号与权限**。使用作者、已接受的编辑者和无关用户。验证撤权与投递并发、读列表后撤权、撤回再重邀、作品进入回收站、账号切换时旧请求才返回。在一页数据中混入失效条目，检查未读和分页都只反映可见行。
- **检查结果**。编辑者完成后，两人各一条且不会再收到普通成功提醒。分别关闭两种分类、作者与发起人重合、其他成员有作品阅读权、零问题、未成功保存结果及旧检查被新检查覆盖的场景都要验。作者打开他人检查时仅获取该次作品概要。
- **投递一致性**。针对同一事件并发写入两次，或业务已提交但调用方未收到确认后补偿，预期仍每人一条。验证禁用期间的事件在重新启用后不会补发。回滚业务、清理任务历史及恢复数据库后，失效链接不能指向另一对象。
- **升级**。用含旧邀请、旧任务和已越线预算的库升级，确认初始无历史未读；另用升级前 79 元、升级后累计 80 元的预算验证首次真实跨档。单书导出再导入，收件记录不随书迁移。

## 验证命令与人工走查

实施迁移时查阅[数据库规范](../../spec/backend/database-guidelines.md)的外键与迁移约定，接入工作台时查阅[组件规范](../../spec/frontend/component-guidelines.md)的布局和任务面板约定。配置隔离测试库时使用[后端质量规范](../../spec/backend/quality-guidelines.md)列明的库名和守卫。

1. 从 `backend/` 运行现有相关回归：`uv run pytest -q tests/test_collaboration_invites.py tests/test_tasks.py tests/test_ai_usage_api.py tests/test_consistency_api.py`。新增通知专项测试随实现按 A1–A7 纳入。
2. SQLite 全量门禁在 `backend/` 执行 `uv run ruff check .` 和 `uv run pytest -n 4 --dist loadfile --durations=20`。PostgreSQL 使用项目规定的隔离测试库，在 `-n 0` 下单独验证迁移、撤权竞争、并发跨档及同事件重复收尾；记录实际运行与跳过项。
3. 在 `frontend/` 运行 `npm run lint`、`npm test`、`npm run build`。使用两个独立浏览器会话模拟作者与编辑者，分别在桌面和 375px 窄屏验证 A1–A7；预算使用本地模型替身触发真实计量。
4. 重点复核实际迁移 head、任务引擎正在演进的终态路径和预算结算事务。数据库迁移与权限查询先通过再接入四类来源；回退时按设计保留个人数据。

需求和验收编号见 [站内通知需求](prd.md)，接口和数据边界见 [技术设计](design.md)。
