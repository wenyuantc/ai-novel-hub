# 登录、两步验证与恢复验收

2026-11-26 在本机使用临时 SQLite、独立的 PostgreSQL 16 容器、共享该数据库的两个 Uvicorn 进程和全新 Chrome 配置完成验收。所有账号、验证器和应用配置均为本次测试生成。下表中的第三方回调由实际 HTTP 路由处理，仅用固定测试身份替换向提供方换取身份的外部网络步骤。

| 场景 | 实际操作与结果 |
| --- | --- |
| 旧账号升级 | 两库均在 0076 创建普通账号，再经 0077、0078 升级；用户 ID 仍为 1，原密码标志为真。PostgreSQL 使用原密码成功登录。继续升级至 MCP 迁移 0079 后，两库仍保留该账号。 |
| 绑定与隔离 | 在进程 A 发起 Linux DO、GitHub 绑定，在进程 B 完成各自回调。两种入口都返回同一旧用户 ID 1。另用两个平台相同的数字身份分别首次登录，得到两个不同的本地账号。同一 GitHub 新身份两个浏览器同时回调，均成功且最终用户 ID 相同。 |
| 授权中关闭注册 | 开放注册时启动未绑定 Linux DO 登录，在 A 用管理设置关闭注册，在 B 完成回调，被拒绝建号。已绑定的 GitHub 身份仍可登录。 |
| 两步验证与跨进程恢复码 | 在 A 生成绑定信息、B 验证动态码并领取十枚不同的恢复码。分别经密码、GitHub、Linux DO 完成第一步，三个客户端访问受保护的用户接口均返回 401。两个独立挑战同时在不同进程提交同一枚恢复码，响应分别为 200 和 400。失败方用另一枚恢复码登录成功，两者仍是 ID 1。 |
| 后台人工恢复 | 超级管理员核实后请求重置，返回 204。普通用户先前的多个会话均收到 401，待验证挑战随即失效。原已绑定 GitHub 身份可重新登录并进入原账号。审计表记录真实管理员、目标 1、成功。 |
| 本机部署者恢复 | 为唯一启用超级管理员开启两步验证，在后端执行 `python -m app.recover_two_step --user-id 2 --confirm`，输出已重置。数据库审计为 `user.two_step.local_recovery`，操作来源“部署者本机恢复”，目标 2、成功；随后可使用原管理员密码登录。 |
| 真实 Chrome | 桌面浏览器从登录页输入旧用户密码，在账号安全页绑定验证器、提交六位动态码、查看并确认保存一次性恢复码。在独立 375px 宽浏览器中用密码和一枚恢复码回到书架。两次流程均未收到页面执行异常。同一隔离实例另由前端验收：1280px 管理员详情页未勾选身份核实时无法确认，勾选后真实请求 204，刷新后重置按钮消失；审计页展示管理员来源、目标、成功结果及独立的部署者本机恢复来源。 |
| 回退保护 | SQLite 副本仅含升级前密码账号时，从 0078 回退至 0076 并重新升级，用户仍为 ID 1。PostgreSQL 中含真实测试绑定后，0078 降级至 0077 被拒绝，提示先处理登录方式。 |
