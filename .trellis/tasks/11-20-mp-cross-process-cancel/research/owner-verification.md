# 本人取消的运行验证

两个应用使用独立连接池、任务引擎和执行者租约。经 HTTP 在 A 创建作品及任务，通过 B 客户端携带同一会话请求取消。测试使用受控模型和隔离数据库。

| 验收项 | 故障与观测 |
| --- | --- |
| AC1 运行中单章 | 基线中 B 已返回 cancelled，A 的模型仍未收到中断（计数为 0）。修复后 A 的实际模型收到一次中断，B 读到 cancelled，一条已取消生成记录，原稿保留、章节回到 draft、原占用已归还。 |
| AC2 分析与向导 | 基线中 B 对活的分析和向导任务均返回 409。修复后在 A 停住模型，B 可以取消分析以及 world、characters、outline、careers 四种向导。受理时核对同一原执行，原有待核对及损坏收据仍有独立的 409 回归。 |
| AC1、AC5 提交与失联 | 在 A 尚未扫描意图的窗口，B 两次请求均在设定的等待预算后返回 running。两次读取的持久取消时间相同。分别放行 A 扫描和在 A 保留慢模型时使原租约失联。两条路径均产生一次原轮次终态，B 能读到 cancelled，A 的迟到输出未修改正文。 |
| AC5 恢复与本人受理竞争 | 令 C1 接管旧无主 running，在原 handler 回退结束后、终态锁前停住。由另一个应用提交取消再放行。原回退成功时任务及统计均为 cancelled；同一停点注入资源身份核对失败时，两者均为 interrupted，原执行键保留。两种情况均只调用一次清理。 |
| AC1 提交确认丢失 | 在真实的本机本人取消入口注入数据库提交异常。写入前失败时模型继续生成并成功保存；写入后只丢回执时，按原任务和入队轮次查到持久意图，模型实际收到一次中断并写入已取消。 |
| AC2 待核对任务的范围 | 原执行进程健康，但指定单章结果待核对且执行体已退出。B 返回 409，数据库保留原执行键。同一作品的另一条健康生成任务仍可从 B 正常取消。 |
| AC10 本地与领取窗口 | 真实本地取消和既有领取提交已生效、回执尚未归来的竞争继续经过原执行身份检查。覆盖本人取消和关停两种信号，两个窗口合计 4 项通过。 |
| AC10 失去权限与原身份 | 累计 63 项既有测试通过。涵盖 `test_collaboration_task_review.py`、`test_wizard_uncertain_cleanup.py`、`test_wizard_execution_identity.py`、`test_task_worker_recovery_crash.py` 和 `test_task_worker_lease.py`。 |

## 双库结果

在 `backend` 下运行 `uv run pytest -n 0 -q tests/test_c3_owner_cancellation.py`。默认 SQLite 的 13 项用例全部通过，耗时 58.20 秒。使用 PostgreSQL 16 隔离测试库串行运行同一文件，13 项全部通过，耗时 109.26 秒。测试通过两个独立应用实例访问共享数据库，模型流在受控停点处理。

将分析与向导的原名额核对合入本人取消和作品删除共用的条件更新后，再以 `-k 'peer_cancel or unproven_exit'` 重验 7 项。SQLite 全部通过（38.72 秒），PostgreSQL 16 全部通过（57.16 秒）。

## 调度器已停止时的定向接管

首次 SQLite 全量回归发现，协作任务权限矩阵已关停调度器，旧的无主 running 接受取消后超时返回 running。请求处理进程现在用自己的租约，只针对该 UUID、入队轮次及执行键执行 C1 认领。已登记的远端执行者必须由权威租约确认停止或失联，才能转交。原 `test_write_surface_matrix` 的作者、编辑者和管理员兼编辑者三项保留原断言并通过（19.98 秒）。

- HTTP 断连后，已领取的旧任务完成取消，同库另一条无主记录仍为 running。
- 健康远端保持原归属；租约失联后 HTTP 才接管，并拒绝旧模型的迟到正文。
- 管理员在 HTTP 接管已提交、尚未开始业务回退时介入。即使本人已断连，原轮次仍完成管理员处理并清除两种请求标记。
- 本人受理之后才发现结果无法核对，接管者保留 running、原执行键及待核对时间。
- 本人提交成功但请求断连，或提交回执和首次确认读均丢失，独立请求执行者仍能依据持久意图完成本轮。
- 未开启调度时删除作品，会排空并删除本作品；另一个作品的旧无主任务仍为 running。

上述 7 个回归节点在 SQLite、PostgreSQL 16 各通过 7 项。SQLite 本人取消、作品删除和跨入口交错联合运行通过 28 项（104.92 秒），另有 C1 租约与接管崩溃回归 24 项通过（68.49 秒）。联合运行时两个提交确认故障及定向作品删除的三个新节点尚未加入，已分别在双库补测。

### 终态与统计事务故障

`test_statistics_failure_rolls_back_terminal_update` 先执行真实统计写入，随后在终态事务提交之前注入 `RuntimeError`。本地请求执行者已持有这一轮次时，等待方重新读取数据库；若任务仍由同一执行者持有、仍为 running 且管理员未接手，原等待请求收到该异常。原用例保留任务与统计均为 running、统计结束时间为空的断言。统计整文件 12 项通过（9.02 秒），既有请求断连、健康远端和本地提交确认选择 9 项通过（15.13 秒）。

反向故障用例在终态已提交之后丢弃提交回执，再让接管者的首次确认读失败。等待方独立读到已提交的 cancelled，任务和统计一致并带结束时间。SQLite 通过（1.40 秒），PostgreSQL 16 通过（4.28 秒）。

## 旧失败重试与新批次

全量回归暴露了未冻结的内部清理入口会为后来出现的 running 批次额外登记取消。用例中 `claim_batch_chapter` 已把新 claim 同时写入批量断点和章节。修复后，重放旧失败仍核对旧单章凭据；要取消新批次，须持有当前作品的删除 token 或加入已受理的同轮意图。原 `test_old_failed_cleanup_never_releases_new_batch_claim` 的冲突、两次旧 claim 和新章节占用断言全部保留。原任务清理与 worker 收尾模块共 32 项通过（27.05 秒）。

新增边界用真实处理器构造批量断点。在没有 token 或持另一个作品有效 token 时均保留原批次和章节占用。随后通过 HTTP 删除本作品，章节与批次凭据匹配时返回 204 并归还占用，替换过占用时返回 409 并保留作品和新占用。SQLite 两项通过（1.90 秒），PostgreSQL 16 两项通过（6.69 秒）。

## 修改的现有测试夹具

`test_admin_task_adversarial.py::test_admin_acceptance_between_owner_check_and_update_is_a_real_cas_barrier` 刻意停掉调度，把管理员唤醒替换为仅记次数，因此持久的 pending 不会自行结束。旧夹具期待请求在 3 秒内返回，这在过去依赖“本机没有 drain 就立即返回”。跨进程后请求需要为远端 drain 预留现有的等待窗口。在该夹具显式设置 `cancel_wait_seconds = 0.05`，保留原来的 3 秒测试超时、两个真实会话的提交顺序、原操作号、任务与统计状态和不得多回退的断言。该组全部 5 个参数通过，应用默认仍为 10 秒。

`test_collaboration_task_privacy.py::test_system_can_cancel_revoked_collaborator_task` 此前把整个 `_abort_loaded_task` 替换为空回调。该替身一并跳过了事务内的清理收据，导致排空等待超时。用例选择的 `outline.continue` 真实处理器没有章节等资源需要回退，已移除这个替身。保留系统成功排空一条任务、任务实际成为 cancelled、已撤权用户仍读到 404 三项原断言。
