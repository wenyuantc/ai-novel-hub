# 0068 迁移、备份与删除屏障的独立复核

## 实际发现与修复

- **SQLite 原生冷恢复。** 原实现会在新副本中围栏旧执行者并归还 C2 名额，但没有归还随该执行体退出的 C3 工作记录。以真实原生快照复现，恢复后仍多出一条归属于已围栏 worker 的活动执行记录。现在冷恢复只移除已确认停止或围栏的正常执行记录。未知 worker 的记录、尚在清理的请求和失败证据仍保留。快照源文件中的原数据不变。用恢复后的应用重新登录并删除原作品，实际收到 409 `project_tasks_not_stopped`，随后可以正常读取作品。
- **命名共享内存 SQLite。** 这类主库的物理文件路径为空，C1 的租约旁库仍有独立的文件及代次。0068 现在读取本次主库事务中的配对身份，核实旁库、文件标识与生命周期锁。用两条实际连接验证 0067 升至 0068，再降回 0067。两个方向都在原租约仍持锁时拒绝，在仅旁库保存活跃执行者而主库尚无登记时也拒绝；原执行者确认停止后迁移成功。

## 兼容与竞争验证

| 场景 | 实际观察 |
| --- | --- |
| 降级与新证据同时写入 | SQLite 和 PostgreSQL 16 均在写入未提交时启动降级，用独立事务提交原清理失败证据。降级随后拒绝，版本保持 0068，原证据仍可读。PostgreSQL 另用 `pg_blocking_pids` 观察到迁移事务确实在等写事务。 |
| SQLite 作品编号及子行 | 在 0067 删除编号 50 的作品，另一个作品仍有任务。实际升降级两次核对最高分配号仍为 50、子任务仍归原作品、外键完整。下一次创建得到编号 51。 |
| 旧外部调用、删除意图与活跃名额 | 两种数据库的原位用例覆盖健康旧 worker、归属损坏的旧名额、可证明原归属及旧删除 token。迁移留下旧业务凭据，清除已停旧服务留下的删除意图。注入 DDL 中断时原列、数据与版本一起回滚。每一类新证据均独立阻止有损降级。 |
| 作品 v16 | 通过真实导出和导入入口往返全部作品资料。源实例的任务、租约、在途记录和删除 worker 均不进入导出的 JSON；导入的作品不会建立或继承外来的运行登记。 |

复验入口为 `backend/tests/test_c3_schema_boundaries.py`、`test_sqlite_lease_pair.py`、`test_backup_sqlite_restore.py`、`test_task_worker_migration.py::test_0068_preserves_legacy_claim_and_guards_work` 和 `test_project_transfer.py::test_round_trip_all_entities`。PostgreSQL 测试使用临时 PostgreSQL 16 专用库，按用例建立独立 schema 并串行运行。

最终独立组中，新的迁移边界、已有 SQLite 配对模块和作品完整往返共 16 项通过，0 失败、0 跳过。另一次联合运行中，两个数据库版本的 0068 往返、冷恢复及结构拒绝用例等共 23 项通过。两组有重叠。定向 Ruff、Python 编译检查、前端 TypeScript 构建和 Git 差异空白检查通过。
