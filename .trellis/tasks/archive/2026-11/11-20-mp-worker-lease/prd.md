# C1 执行者登记、租约与启动恢复不误伤

> 父任务：`.trellis/tasks/archive/2026-11/11-20-multiprocess-task-scheduling-deploy-drill`（需求全集见其 `prd.md`，总体设计见其 `design.md` 第 2 节）。本子任务无前置依赖，是 C2–C7 的基础。

## Goal

让数据库能回答「这条运行中任务的执行者是否还在」。在此基础上，进程的启动、重启与周期恢复只处理执行者已确认不在的任务；执行进程失联后，其任务在有界时间内由存活进程收尾。

## Background

- `tasks` 表没有 heartbeat／owner／lease 列；`execution_key` 标识领取代次，且被排队取消清理标记、成功回调未完成、收尾失败屏障、管理员取消收据复用（`backend/app/services/task_engine/engine.py:1294,2707,2769-2779`；`task_service.py:1186-1193`；`task_engine/cancellation.py:206-241`）。
- `recover()` 读出全库 `status == 'running'` 的任务，只跳过本进程登记的（`engine.py:440-442`），其余全部按遗留收尾，注释多处写明前提是「旧进程已排空」（`engine.py:451,462,513,552`）。
- 启动时 `recover_external(stale_only=False)` 把全库 executing 的外部调用判为失败（`engine.py:578-583`；`agent/service.py:147-154`）。
- `stop()` 只中断本进程登记的任务（`engine.py:304-335`），多进程下语义不变。
- 0065 的约 30 个恢复类用例用「手工写成 running 再 `start()`」模拟崩溃（父任务引擎调研第 10.1 节）。两组共享 SQLite 的故障对照已验证单章和向导在两次提交之间丢失凭据的结果，见 `research/recovery-reentry.md`。
- 两个真实进程在 0065 上完成了 SQLite 争用基线，心跳采用独立短事务模拟。正式租约、接管与 PostgreSQL 仍需实现后验收，见 `research/sqlite-contention.md`。
- 首版 SQLite 单文件租约遇到真实 SDK 慢请求会因发送事务占住写锁而误中断健康任务。2026-11-23 用户确认 SQLite 使用主库旁独立的租约文件，并要求实施及验证。故障和 PostgreSQL 对照见 `research/sqlite-slow-provider.md`。

## Requirements

- **R1 执行者登记**：每个应用进程启动任务引擎时在数据库登记唯一身份，并按固定间隔更新心跳；正常停止时标记已停止。
- **R2 任务归属**：领取任务时，任务的执行者身份与 `running` 状态、`execution_key` 在同一条条件更新中写入。
- **R3 孤立判定唯一**：提供唯一的「孤立运行中任务」判定——状态为运行中、未被恢复处理过，且没有执行者身份或其执行者不存活。存活判定只使用数据库时钟。
- **R4 恢复只处理孤立任务**：`start()` 中的恢复与新增的周期恢复都只处理孤立任务；存活执行者的运行中任务不被读取为遗留、不执行 `on_abort`、不改状态。
- **R5 接管唯一**：多个进程同时发现同一条孤立任务时，只有一个进程执行收尾；接管进程中途失联后，其他进程可以再次接管。
- **R6 失联收尾有界**：执行进程被强杀后，其运行中任务在「租约期限 + 一个调度周期」内按现有恢复规则收尾（按收据完成、转待审核、保留待核对或记为中断），占用被释放。
- **R7 自我围栏**：进程得知自己被判定失联，或无法在租约期限内更新心跳时，停止领取并终止本进程的全部执行体，这些执行体不再产生任何任务写入；随后以新身份重新登记并恢复调度。
- **R8 待核对状态持久**：恢复决定「保留运行中待核对」的任务，其待核对标记持久化，任一进程读取任务时都显示「结果待核对」，且不被周期恢复反复处理。
- **R9 外部调用的启动恢复不误伤**：启动时不再无条件把 executing 的外部调用判失败。本子任务先收紧为：启动与周期恢复只处理超过现有过期阈值（2 分钟）的调用；按发起进程精确判定在 C3 完成。单进程崩溃后，遗留的 executing 调用因此最迟在阈值加一个调度周期后被判失败，而不是启动瞬间。
- **R10 SQLite 争用基线**：实测两个进程共享一个 SQLite 文件时并发领取、心跳、刷库的等待与超时，确定统一的 busy 等待与有限重试策略，并写入规范。
- **R11 单进程行为保持**：单进程部署下，正常停止后重启的恢复时机与结果不变；现有恢复类用例在不改断言含义的前提下通过。崩溃后立即重启时，遗留任务的收尾延后到旧租约到期，这一变化写入规范。
- **R12 迁移**：新增表与列的迁移在 SQLite 与 PostgreSQL 上可升级；存在未停止的执行者登记或带执行者身份的运行中任务时拒绝降级。
- **R13 SQLite 文件配对与冷恢复**：同一 SQLite 主库的执行者共享独立租约文件，主库长时间持锁时健康进程仍能续约。租约文件丢失、损坏或替换后须停止沿用旧身份。运维人员在停止所有旧进程后，可用原生主库快照冷恢复，并使旧身份永久失效。PostgreSQL 使用主库登记行续约。

## Acceptance Criteria

- [x] **AC1** 双引擎测试：引擎 A 运行任务期间引擎 B 启动，A 的任务继续并成功结束，期间状态从未变为中断，`on_abort` 未被调用。（R4）
- [x] **AC2** 双引擎测试：A 运行任务时使 A 的租约过期且不再心跳，B 在一个调度周期内把任务按规则收尾并释放章节占用；A 的执行体随后的写入全部失败关闭，库内正文与状态不被 A 改动。（R5、R6、R7）
- [x] **AC3** 双引擎测试：两个引擎同时对同一条孤立任务执行恢复，`on_abort` 只执行一次，任务终态只写一次，任务统计只记一次。（R5）
- [x] **AC4** 第三个引擎在接管者租约到期后能继续收尾。对单章占用及带有效未提交凭据的向导，分别在认领后、资源修改后尚未提交、提交已成功但确认丢失三个位置注入故障。任务终态、执行键、章节占用、向导内容、项目清理屏障及统计均与正常完成一次的对照组一致。原本缺失或损坏的凭据继续按各自既有规则处理。（R5、R7、R11）
- [x] **AC5** 被围栏的引擎停止领取、清空执行体，并以新身份重新登记后可以领取新任务。（R7）
- [x] **AC6** 分析与向导任务被恢复为「保留待核对」后：两个引擎读取该任务都显示待核对；后续调度周期不再对它执行恢复逻辑；它不占并发名额与串行键。（R8）
- [x] **AC7** A 有外部调用处于 executing 且未超过过期阈值时 B 启动，该调用状态不变；已超过阈值且无本地在途调用的记录能由恢复逻辑置为失败，且不重新调用外部服务。（R9）
- [x] **AC8** 现有恢复类用例（父任务引擎调研第 10.1、10.2 节所列）全部通过；被改动的用例在提交说明中逐个列出原因。（R11）
- [x] **AC9** 两个真实进程共享一个 SQLite 文件并发运行领取、心跳、刷库的压力脚本，记录等待分布，无未处理的数据库忙异常；结论与参数写入规范。（R10）
- [x] **AC10** 迁移在 SQLite 与 PostgreSQL 16 上升级通过；有活动登记时降级被拒且数据不变；空库往返通过。（R12）
- [x] **AC11** PostgreSQL 16 上串行通过 AC1–AC4 对应用例。
- [x] **AC12** `uv run ruff check .` 与 SQLite 全量回归通过。
- [x] **AC13** 真实 SDK 请求在服务器收到完整请求后等待 32 秒才返回响应头，原执行者仍以同一身份完成，正文完整，其他活执行者的心跳也能提交。两文件注册或围栏之间退出后可收敛；文件缺失、替换以及冷恢复均不会让旧身份写入。主库持锁期间可判定侧库失联，主库恢复可写后下一调度周期可继续接管。（R5、R7、R11、R13）

- 内部通道与 `peer_url` 的使用（C4）；本子任务只建列。
- 备份运行器的启动恢复（C5）。
- 管理端展示存活进程（C6）。
- README 的限制说明改写（C7）。
