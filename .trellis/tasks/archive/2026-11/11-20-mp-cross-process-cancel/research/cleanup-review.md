# 取消清理中断与接手复核

## 复现与修复记录

1. 本人取消处于排队或暂停状态的任务，业务回退和回执已经提交，HTTP 请求随即中断。即使原请求执行者已确认停止，另一个应用删除作品仍返回 409。SQLite 上两个逐项回归均复现，章节上的测试计数已为 1。修复后，请求在第一次状态提交中保留原轮次、资源凭据和清理阶段，接手方按回执决定是否还需执行业务回退。排队和暂停各在业务提交前后中断，四项均转为 204，计数均为 1。
2. 排队任务的本人清理中断后，管理员可以针对同一轮任务取得 202 及操作编号。管理员处理会避让已经保留的排队执行标记，原请求的恢复又要求没有管理员意图。SQLite 的两个故障时点均复现，管理员后台返回后，实际删除作品仍得到 409。修复后，管理端凭原操作编号、原入队时间与执行标记接回已经退出的清理。独立回归分别让管理端先处理，以及延后受理时的唤醒，让作品删除先发现原操作。业务提交前后两种中断时点，每个入口均完成一次清理，保留一笔原受理审计。

## 检查方法

- 两到三个应用实例共用测试数据库，各自建立会话工厂、工作者代次和任务引擎。时序用事件或请求中断来控制，再从其他实例重读已提交的资源计数、任务状态、清理记录和审计。通过持久化租约停止标记模拟工作者失联后的确认状态。
- 持久失败重试者在执行业务前、提交业务及回执后分别失联。后继实例通过作品删除入口接手，恢复迟到的旧协程后，再核对业务计数为 1 且作品已软删除。两项在 SQLite 和 PostgreSQL 16 上通过。
- 管理员收尾连续失去两个处理者。第一位持有清理权但尚未开始业务，第二位已提交业务和回执，第三位完成任务终态与统计。随后释放前两位的协程，独立连接仍只能看到一笔业务效果、一笔成功审计，原清理记录已归还。
- 软删除后如果出现无法证明归属的清理失败，仅原实例有内存标记。另一个实例发起人工永久删除得到 409，模拟保留期届满的清理批次删除数为 0。原作品与失败记录均保留。此项在 SQLite 和 PostgreSQL 16 上通过。
- 既有身份回归覆盖同一个任务换轮、原批量章节已由新任务占用、旧任务统计 UUID 被替换和缺失原清理快照。冷恢复回归使用真实 SQLite 快照，检查已确认停止的普通执行、未知执行者、未结算清理和失败记录。并跑管理员实际章节及批量取消，SQLite 交叉组共 30 项通过。

独立回归在 `backend/tests/test_c3_cleanup_recovery.py`。章节计数由测试处理器通过真实的数据库提交写入，能区分业务生效零次、一次和重复生效。生产处理器的资源、正文和统计断言另见 `test_c3_admin_cancellation.py`、`test_task_abort_identity.py` 与 `test_c3_schema_boundaries.py`。

## 验证结果

- SQLite 独立模块 12 项全部通过，耗时 17.31 秒。使用真实排队、暂停两种拆书任务状态启动取消，并核对任务统计的最终状态。旧身份、冷恢复及管理员交叉组 30 项全部通过，耗时 67.76 秒。
- PostgreSQL 16 单独先行验证了失败重试者两种中断时点、永久删除与过期清理三项，全部通过。完整 PostgreSQL 串行组由主会话记录。
- 全后端 Ruff、受影响 Python 文件编译、前端 TypeScript 构建和 Git 差异空白检查通过。项目后端未配置独立的静态类型检查命令。
