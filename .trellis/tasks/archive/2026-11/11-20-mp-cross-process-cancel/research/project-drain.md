# 作品删除、执行退出与请求侧收尾

- 研究问题是当应用 B 删除作品时，哪些持久事实能证明应用 A 的执行链或清理已经结束，以及哪些事实只能用于安全重试。
- 范围为本仓库后端源码、既有测试与 Trellis 规范。
- 日期为 2026-11-23，基于 C2 的 0067 结构。

## 持久排空口径

1. 建议在 0068 为 C2 槽冻结可空 `project_id` 并索引，在领取事务从原执行身份写入，排空按槽本身查询。项目外任务的空值需与无法归属的旧占用区别。升级使用停旧执行者、排空和核验流程，对仍在用但不可安全归属的槽拒绝升级，保留证据；不通过今天恰好占用同一整数任务 ID 的行回填。可参考 `backend/tests/test_task_slot_lifecycle.py:33` 现成的成功、清键、终态发布及围栏交错。
2. 删除两阶段保留原作品父行锁和复核顺序。进程 B 写入带本次删除 token 的逐轮取消意图；执行者自己取消。等待时使用独立短事务并传递剩余限时，允许本地事件缩短等待。二次锁内同时检查原有开放任务、收据、章节、外部调用、带作品身份的执行槽，以及下表中的请求工作与失败记录。永久清理和到期清理使用同样的锁内口径。删除请求所持的本次协调身份，可用精确 token/工作 UUID 排除自身，不能排除同 worker 上的其他工作。统计受本次删除实际影响的任务时，跨轮/ID 复用须按原身份去重。
3. 对存活执行者，若删除承诺等待原 asyncio 执行体真正退出，正常回调的退出确认应在原执行体完成后产生；在归还槽已经提交、但回执尚未送到且 `_on_done` 尚未执行处设屏障，可验证是否需要独立退出确认。C1 围栏撤销后续写入权，不能证明被冻结的操作系统进程、第三方效果或旧 Python 协程物理终止。每项可能跨事务的清理写入均要在本轮工作身份和原 worker 权限下复验；仍有未决外发、收据或清理归属时持续阻止删除。
4. 删除意图新增发起 worker 代次，与 token 同笔提交。等待后、最终删除时也复核原代次仍有资格、本次 token、原作品、操作者及权限；迟到旧请求不得清别人重试的新 token。释放的 CAS 应包括原 token 与 owner。启动或周期恢复只解除已持久确认停止或围栏的原主的删除意图，永不代替旧请求完成软删。定时复查覆盖「B 启动时 A 尚活，随后 A 突然失联」的情形。workers 注册时会裁剪历史登记（`workers.py:258`），仍被删除意图、请求工作、外调或恢复证据引用的登记须保留，或在裁剪前将不可逆确认转换成持久状态。非空 owner 没有可核验登记时保守处理。旧版无主 token 只在已确认旧服务下线的迁移/冷恢复边界解除，不把当天新写但损坏的记录视为旧意图。
5. 主应用将 owner 判定放到已注册并已核验 C1 SQLite pair 的生命周期内，安排在任务开始调度和回收站清理器启动前。HTTP 请求归属不能依赖调度器一定在跑，既有 `backend/tests/test_recycle_bin_tasks.py:90` 先停止引擎再受理排队取消和删除，此时 `WorkerLease.stop` 已清 worker key。建议请求使用覆盖 HTTP 生存期的租约或把请求归属与调度启停解耦，共用 C1 判活协议。正常停机等待请求退出后才确认停止，租约失效时也要处理仍在执行的请求。`engine.py:388` 的换代当前只等待 `_running`，而 `:451` 的停机还等待请求侧清理。禁止旧代协程借用新代身份。

## 各类屏障及其寿命

| 本地事实 | 建议持久口径与安全重试 |
| --- | --- |
| `_cleanup_work` | `engine.py:3215` 在同一协程内按作品嵌套计数，`project_work` 排除当前协程。底层入口包括本人取消外层与内层（`task_service.py:1023,1076`）、管理员 drain（`cancellation.py:284`）、协作待审扫描（`engine.py:1244`）、智能体手工和后台外发（`agent/service.py:1015`、`agent/runner.py:524`）。分别绑定工作 UUID、作品、owner 代次、用途及原任务/外调/管理员意图，外层登记一次，独立并发工作分别持有。应在第一次让外部工作或任务状态可见的事务内预登记，并保持到最后的回调/授权投影/发布退出。父行或 authz 写锁已在调用方事务时，另开连接补登记会等待自己；应复用该事务。等待另一个管理员 drain 的客户请求不能加入会被该 drain 等待的工作集合，需区分观察者与实际修改者。 |
| `_abort_failures` | 现有值是作品 ID 集合，不能让一个成功清理消除另一个失败。建议按作品查询仍开放的持久失败事实，供所有进程和 purge 共用。保留此集合时只作本地提示。 |
| `_failed_cleanups` | 需要支持下一次删除对可证明的旧失败重试。以独立工作 UUID、原 task UUID/轮次/execution/worker 和资源收据存冻结证据，允许在远端精确重放现有 `_retry_failed_cleanup`。只保存能还原原 claim 的必要类型化字段与校验摘要，对现存输入与断点核对后才能采用；如确需保存原业务片段，在内部记录严格限制用途、读取和寿命。不要使用 pickle，或把原始正文、请求头、凭据写入审计/日志。持久预登记或未确认工作必须连续覆盖故障写入、释放提交和两者的未知回执间隙。成功后只确认同一工作，并再次核验业务收据，不能释放另一轮。 |
| `_unproven_abort_failures` | 捕获不到原身份、同一 ID 下原快照冲突、未确认的终态写入各有入口（`engine.py:506,916,1640,1705,1734`）。保留作品级的持久“未能证明”记录，与可重试的原快照分别处理。仅能由对同一事实的明确原始收据/恢复协议推进。TTL、worker 换代、任务已经裁剪、后来出现一条看似相同的新任务、同作品另一项重试成功，均不能清除该记录。找不到可靠证据继续返回 409。 |
| 归属已停止的在途工作 | 原 worker 无写权后，按冻结的原身份复核业务提交和外部收据，已证实完成的可以归还，可证明未完成的由唯一处理者受限重试，其余转成持久未确认屏障。C1 的 `_release_confirmed_slots` 适合归还调度名额，不能照搬成删除所有请求/收尾证据。冷恢复见 `sqlite_lease_pair.py:231`，同样须保留业务失败、未决外调和待核对记录。 |

## 实施时的定向验证

- A 的运行任务由 B 删除，拦住 A 的取消和最后发布，以独立会话核对作品删除 token、软删时间、取消终态和成功审计。冻结成功回调时让 Task 行先被裁剪，再建立同 ID 的别的任务。B 仍须等原作品的工作结束。对正常存活 owner 另设归还提交后回执延时的停点，核实 A 原执行体真实退出。
- A 的 queued 取消已提交终态，但请求后续清理未退出。B 在删除中冻结新写入，等待准确工作 UUID。覆盖同进程嵌套、两个并行清理、管理员意图和本人等待并发、调度已停止、客户端断开、已经持父锁时登记、登记/归还回执丢失。每处等待释放 DB 锁，作品移入回收站后保留现有本人响应的身份复核。基线见 `test_recycle_bin_tasks.py:90,148,184,255` 和 `test_task_abort_identity.py:218`。
- 触发 A 的可证明 handler 异常，B 第一次删除失败，安全重试只能用原轮次。替换原 claim、Task、章节/批量游标，分别验证 409 与新资源完整。构造没有快照的失败、无执行键的终态、只剩持久屏障的作品，验证 B 重启和原 worker 围栏后 soft delete、purge、expire 均不越过。基线见 `test_recycle_bin_tasks.py:231,300,328,381,398,467`、`test_task_abort_identity.py:32,49,67,90,147`。
- A 持意图时启动 B。暂停 SQLite 主库更新让侧库先决定失联，B 只有在主库能提交确证后才动该 token；新实例抢先领取同作品新 token 后，A 的迟到 finally 不影响它。覆盖 A 正常退出、长期冻结后复活、B 启动后才失联、冷恢复、旧无主意图、活动但陌生的 owner。两方言检查 final 检查与并发登记并行时写入顺序。原 `test_project_lifecycle.py:193` 代表旧版孤立意图的兼容分支。
- 迁移/作品传输登记表变动包括 `project_transfer/registry.py:177` 的 `PROJECT_RULE.exclude`、实例级运行表、`app_schema`、备份冷恢复以及从 0067 双向升级/降级。持久失败、待核对收据、活动 worker 与请求或未释放槽存在时应拒绝会丢证据的降级。SQLite 重建作品表需保留所有子表、外键及 AUTOINCREMENT 高水位。参考 `backend/tests/test_recycle_bin_migrations.py`、`test_task_worker_migration.py`、`test_task_worker_slot_reclamation.py`。
