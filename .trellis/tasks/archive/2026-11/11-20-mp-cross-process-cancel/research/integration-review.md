# C3 全范围集成评审

评审以含 C1、C2 的 `d2908f0` 为比较基线。按包索引核对后端、前端接口、运维升级与验收脚本。逐项检查受理、领取、执行、回退、结果投影和释放各自使用的事务与持久凭据。

## 跨层检查

| 行为 | 源码与实际观测 |
| --- | --- |
| 本人取消与返回权限 | 同一任务 UUID、入队时间和执行 UUID 绑定取消请求。两进程实测，受理方先持久写下意图，原执行者才关闭模型连接、归还章节占用并写一条取消记录。等待期间登录令牌被撤销则返回 401；同 UUID 重新入队返回 409；被另一账号复用的整数 ID 返回 404。详见[交叉验收](cross-entry-verification.md)和[本人取消验证](owner-verification.md)。 |
| 管理员与执行者 | 管理员受理沿用一个操作号和一次成功审计。对排队、待审核及旧无主工作，认领条件包括原轮次和操作号。业务回退的独立会话借用同一连接的保存点，回退效果与处理收据一起提交。对活的远端运行任务，原执行者承担真实取消；有管理意图时的批量收尾需匹配具体操作号，常规发送和结果检查仍须原执行身份。 |
| 执行名额与删除 | 原执行 UUID 在领取事务内同时取得 C2 名额并登记作品工作。名额可先归还，原执行协程退出且从索引摘除后才确认作品工作退出。软删除的最终事务复核原 token、作品、权限和请求 worker，并查询任务、在途工作、失败及未决外呼。永久删除和过期清理经过同一空闲检查。真实模型 TCP 服务和独立观察库均见[双进程记录](sqlite-http-cancellation.md)。 |
| 请求生命期和恢复 | 应用启动时先登记请求 worker；停止调度后它继续心跳。停止应用时等待使用该身份的请求和后台清理退出。已停止或围栏的状态保存在主库；SQLite 先核对配对旁库。仍被清理、删除或外呼引用的终止登记会保留，恢复据此判断原处理者是否已失权。 |
| 外部工具 | 手动确认绑定请求 worker，自动路径绑定任务 worker。签名、重新核对权限、实际发送和结果更新均关联原 claim 与不变身份。结果与活动记录的归还同事务；已退出但结果未知的原工作按已有两分钟阈值处置，仍健康的慢调用可继续。覆盖受控 MCP 服务、失权后的迟到响应和实际请求次数。 |
| 迁移与对外格式 | 0068 的 SQLite 离线配对和 PostgreSQL 表锁覆盖前置检查。旧槽需可核对原轮次；待核对的工作或收据会阻止降级。原生快照冷恢复按旧租约处置执行工作并保留失败证据。单书 v16 只更新 `app_schema`，实例运行字段不进入导出。详见[迁移独立评审](schema-review.md)。 |

从两版应用的正常入口生成 OpenAPI，排序后的 UTF-8 JSON 均为 415 条路径和 922560 字节，SHA-256 均为 `648c9f60829c4f526ad4cf02ceefa95c33c269042d3bca102e4290610ebf91af`。SQLite 临时库演练已由 0067 正常入口创建作品，升级至 0068 后读取，再降级，用 0067 重新登录并读取同一作品。[离线回滚记录](verification.md)

## 评审中的故障检查

- 已退出的 MCP 请求首次未能写入退出状态时，健康 worker 会阻止对端恢复。复现将故障注入更新 SQL 与提交之间。修复后原处理者在仍持该租约时用新事务重试，相同 claim 只发送一次；迟到的旧结果不能覆盖已核对状态。
- 本人请求退出时的已结算记录同样会因暂时写入失败遗留。现在原 worker 按同一工作 UUID 确认退出。对于仍有业务步骤的请求，接手方区分副作用提交前后两个阶段。删除失败后的重试另设尝试 UUID，领取回执不明可查回原尝试，旧请求退出时只归还自己持有的尝试。[取消清理中断与接手复核](cleanup-review.md)
- 管理员已停止调度但仍可处理 HTTP 时，清理归还暂断、排队清理的领取回执丢失，以及在线认领旧无主任务后丢回执，都会留下健康 worker 的未决操作。现由请求心跳派发独立的确认工作，不占用 SQLite 旁库续约。原操作号只在主库成功核对后解除；第一次重读仍失败时，下个周期继续。领取与归还均核对原操作及尝试，重复受理共用一项审计。
- 独立 HTTP 演练脚本位于后端包外。从仓库根与 `backend/` 运行 Ruff 时，对 `tests` 顶层包的分类不同。显式拆分脚本的测试工具导入组后，两个目录使用后端配置分别检查迁移和脚本，均通过。

## 独立复验

- 按后端 `pyproject.toml` 执行全量 Ruff，再显式检查 0068 迁移与包外双进程演练脚本。二者均通过。前端 `tsc -b --pretty false`、Python 编译及 Git 差异空白检查均通过。
- SQLite 单独复跑 `test_c3_worker_activity.py` 的请求生命周期和原执行退出确认。停掉调度后请求租约仍有效，正常停止后拒绝旧代次。名额归还后原协程仍在时，对端仍能查询到执行工作。在退出确认写入前发生故障，以及提交后丢回执，两种情况下原工作均被正确归还。共 3 项通过，耗时 3.14 秒。
- 对最终管理员和请求收尾代码复核了每次登记、业务回执、确认及归还的身份条件。管理员 SQLite 回归 87 项、PostgreSQL 16 双应用专项 12 项通过；额外把领取提交与首次重新读取都设为失败，普通排队任务和旧无主任务两种参数在两库再次通过。请求清理、恢复、原任务身份及执行围栏的 SQLite 联合复验 51 项通过。
- 独立进程和故障专项测试有交叠。SQLite 后端全量与 PostgreSQL 16 串行专项的最终收集数和结果由[综合验收记录](verification.md)列出。

生产部署仍遵循当前单进程约束。C3 的跨进程投递依靠轮询。即时唤醒及跨进程订阅由 C4 负责，正式多进程部署由 C7 验收。外部服务收到请求后的第三方效果按现有未知结果处理。
