# C3 跨进程取消与作品删除验收

## 对照基线

基线为包含 C2 的本地提交 `d2908f0`，应用数据库版本 0067。C3 功能提交为 `b476666`，应用数据库版本 0068。独立临时检出中，旧无主单章的管理员取消、停止调度后的请求清理、运行中回退失败后再次删除、外部调用越过阈值时识别本机清理这四项既有回归均通过。基线 OpenAPI 共 415 条路径。

在两个应用中运行原版本时观察到以下区别。

- 普通生成任务在 B 返回已取消时，A 的实际模型调用仍在运行。对同样正在 A 执行的分析或向导任务，B 返回 409。
- 让两个管理员处理者同时看到排队或暂停的同一操作，第一方的清理还阻塞时，第二方已经把任务改成已取消。
- A 的真实 MCP 请求已交付，工具端仍在发送响应正文；调用越过两分钟后，B 回收了这次仍在途的调用，A 最终返回 409。
- 在两个独立 uvicorn 进程中暂停原执行进程，让另一进程取消任务或删除作品。后者已经返回 200 或 204，模型连接仍在，原执行名额仍为 1。恢复原进程后才观察其实际退出。

## 验收环境

SQLite 使用临时文件。PostgreSQL 16 使用本机独立容器和专用测试库，测试按各自随机 schema 运行。真实进程演练使用临时作品、受控模型和两个不同 PID。

## 接口与离线回滚

在临时 SQLite 文件上，从原 0067 应用的正常 HTTP 接口注册用户并创建作品。关闭原应用，升级到 0068，重新登录并读取同一作品；关闭新版，降级到 0067，重新启动原版，登录和读取再次成功。两次 GET 均为 200，用户 ID、作品 ID 和标题一致。

前后两版从实际应用生成的 OpenAPI 文档均含 415 条路径，排序序列化后逐字节一致。前端 TypeScript 编译通过。C1 租约、C2 调度约束、执行槽生命周期和回收四个完整模块在集成后重跑 34 项通过。

## 验收标准与观测

| 验收项 | 从哪一端观察到了什么 |
| --- | --- |
| AC1 本人取消 | B 受理，A 实际关闭模型连接。原章回到草稿，原占用归还，只写一条取消日志。提交前断开时模型可继续，提交后丢回执仍能按原轮次取消。[双进程 HTTP 演练](sqlite-http-cancellation.md) |
| AC2 分析与向导 | 分析任务和 world、characters、outline、careers 四种向导均可由 B 取消。单个执行已退出但结果待核对时仍返回 409，同作品的其他正常任务可以取消。[本人取消验证](owner-verification.md) |
| AC3 管理员取消运行中任务 | B 返回 202 并给出操作号，重复受理共用同一号、一次成功审计。单章和批量的原执行者 A 执行中断。批量已经保存的正文、成功结果和待审核断点保留。断连、撤权以及本人与管理员竞争均对同一轮次核对。[交叉验收](cross-entry-verification.md) |
| AC4 管理员取消排队或待审核任务 | 两个处理者互换认领顺序。独立数据库连接核对业务回退只生效一次，管理员受理审计一条。后续接手者按业务收据从中断处继续。[清理故障验收](cleanup-review.md) |
| AC5 原执行者失联 | C1 先确认失联、认领原轮次，再按业务收据核对结果。在线取消可证明归属的旧无主单章得到 cancelled，启动接回遗留管理意图得到 interrupted。接管者再次失联时沿用首次认领的处理方式。迟到的本人请求遇到任务换轮返回 409，遇到其他用户复用整数 ID 返回 404。[交叉验收](cross-entry-verification.md) |
| AC6 删除等待执行体 | 即使并发名额已经释放、原任务行已裁剪或整数 ID 已分配给另一作品，原执行记录仍阻止删除。收到真实 DELETE 的 204 后第一次读库，原执行工作为零、章节占用已释放。[双进程 HTTP 演练](sqlite-http-cancellation.md) |
| AC7 清理失败阻止删除 | 应用 B 可从主库看到 A 的未结清理。能证明原资源的失败可接手重试，业务只生效一次。缺少凭据的失败继续阻止软删除、永久删除和到期清理。[清理故障验收](cleanup-review.md) |
| AC8 删除发起者的存活判定 | A 持有删除 token 时启动 B，A 仍能完成。确认 A 停止或失联后，B 才能解除原 token。旧请求的迟到归还无法清除新 token。停调度仍能受理 HTTP，关闭应用会等在途请求结束。见 `test_c3_project_deletion.py`、`test_c3_worker_activity.py`。 |
| AC9 外部调用 | A 的真实 SDK 对本机 MCP 服务发送请求，B 在健康慢调用越过阈值后仍读到 executing。确认原 worker 停止后才把未知结果记为失败。实际发包前后两种故障分别观察到 0 和 1 次工具调用，迟到结果及重复确认均未重发。见 `test_c3_external_ownership.py`。 |

## 全量回归中发现的兼容问题

旧版依赖任务调度器关闭后仍可通过 HTTP 取消无主的运行中任务。在 0067 复跑协作权限矩阵的作品作者、编辑者、兼任编辑者的管理员三项，全部通过。0068 第一次全量运行中，这三项在 `outline.continue` 的本人取消上出现差异。单独重现时，接口返回 200，但十秒后原任务仍是 running。初版只有后台调度器会发起接管。

修复把这个兼容入口接回 C1 的数据库认领。HTTP 请求执行者只核对已登记本人意图的原 UUID、入队时间与执行 UUID，按原轮次和业务收据收尾。已有执行者仍健康时继续由其处理。三项既有权限测试使用原断言复验通过。

另一次回归中，重试旧章节任务的失败清理时，同一作品的新批量任务已占用该章。原清理可以凭旧快照重试；要向新的运行任务发起取消，必须先有属于该作品、且仍有效的删除意图。此前排空函数在没有这个凭据时也认领了后来的批量任务，原 0067 用例要求保留新占用。修复在写新取消意图的事务内核对作品和删除身份。经正常 HTTP 冻结删除后，仍可按新任务自己的占用凭据完成删除。

对于已由本机 HTTP worker 认领的旧无主任务，终态事务和统计必须一起提交。故障注入写入统计后抛出异常，原任务与统计均回滚为 running，等待的调用方收到原异常。若终态事务其实已提交、只有接管者的确认和首次核对读取失败，等待端能读到原轮次已取消。原统计文件 12 项和新增双库故障场景通过。[本人取消与统计回滚](owner-verification.md)

同一 pytest 进程中先运行旧清理用例，再运行新增的失败重试，两组参数都未触发注入的故障。单独运行新模块时七项全部通过。原因是旧测试在单例处理器实例上还原绑定方法，新增用例却在类上替换方法。改为只在该实例上注入并还原，保留原异常、重试次数、资源身份与失败证据的断言。同进程按原顺序复跑前置用例与新模块，八项全部通过。此处只改动测试故障注入。

## 请求清理和失败收据

本人取消排队单章任务时，在终态提交后暂停原请求。第二个应用能看到原任务 UUID、轮次和请求工作者对应的收尾记录，并一直等到原请求完成授权投影，才返回作品已删除。另一组测试由原应用生成一次清理失败，保留输入、断点摘要和原资源凭据。另一应用只能重试同一份任务。替换输入后返回 409，失败记录继续保留，库内凭据不含测试草稿。

清理过程中断的逐项结果见 [取消清理中断与接手复核](cleanup-review.md)。另在 SQLite 注入两次连续的退出写入失败，以及两次提交成功后丢失应答。两种情况下原工作者始终健康，原请求确认退出，作品没有遗留清理记录。失败重试的领取应答丢失、业务失败、归还写入失败和应答丢失也在一次测试中连续注入。第二个应用随后领取原失败项并完成，原工作者仍健康。已受围栏的工作者再次报告同一任务失败时，不会重建已经处理的屏障。

旧轮次的管理员操作已完成，新轮次单章取消时第一次释放章节仍可能失败。注入释放故障后，原子取消事务与清理登记一起回滚。持久失败凭据仍记录本次原始章节占用，下一次删除作品按原轮次完成章节释放。历史回归在 SQLite 上通过。

SQLite 最终串行复验覆盖 `test_c3_cleanup_work.py`、`test_c3_cleanup_recovery.py`、`test_task_abort_identity.py` 和 `test_task_worker_handler_fencing.py`，51 项全部通过，耗时 82.49 秒。清理模块、共享引擎与任务服务及对应测试的 Ruff 检查通过。
