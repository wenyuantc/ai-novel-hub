# C6 排空开关设计

当前工作基线为 `codex/mp-peer-channel-stream` 的 `c38d471`。C5 已归档，当时的 Alembic 头为 `0069`。排空由受理时的数据库判断、已有执行者的自然退出及只读管理投影组成。

## 开关与受理事务

- 在系统设置白名单添加严格布尔值 `task_admission_closed`，代码默认 `false`。延续 C2 的部署基线、后台覆盖、逐项恢复、版本冲突、持久审计与提交后发布。设置管理读取需要 `settings.read`，保存需要 `settings.update`。公开配置继续只发注册与 MCP 两项。
- 受理和设置保存共用 `authorization_service.gate` 的根事务写屏障。沿既有锁序取得门禁，使用 `effective_settings(db)` 读共享持久值，再执行受理操作并在同一根事务提交。SQLite 使用既有首条 DML 写门禁，PostgreSQL 使用既有锁与快照约定。peer 通知和定时重载只负责唤醒，阻止受理无需等通知。
- 对已认证且命中任务入口的请求，在模型预检或重工作前用短读快速返回维护错误。最后一次判定在写屏障后，位于模型受理证明消费、资源占用与入队之前。快速读结束后才进入后续锁序，测试覆盖开关在预检后翻转。原有 actor、grant、模型来源、任务 UUID 与入队轮次校验仍全部执行。
- 开启时合法的任务动作返回 HTTP 503，正文为 `{"detail":"系统正在维护，暂不受理新任务，请稍后再试","code":"task_admission_closed"}`。设置不可读或提交待确认沿用既有设置不可用错误。维护拒绝由业务异常统一处理。提案等携带调用方事务的入口由其事务边界负责回滚，维护错误保持原类型和值。
- 领取、正在运行的任务、结果保存与流转发维持原路径。正常状态下的排空开关与设置不可用时暂停领取的保护分别判定。

## 入口与事务边界

| 来源 | 接入点及结果 |
| --- | --- |
| 新建、重试、显式继续 | `task_service.create_task` 在认证写门禁之后判定，覆盖重试的最终插入和智能体提案的保存点模式。`resume_task` 在本人原任务及项目写门禁下判定，再执行恢复校验和状态更新。`task_engine/admission.py` 的预检阶段在 DNS 前快速判定。 |
| 批量分析、拆书导入、知识库 | 普通单项与批量受理接入同一检查。拆书导入会先写作品和章节，知识库上传与重建索引会先暂存文档或清理旧索引。涉及入队的路径在这些写入或耗时处理前判定，异常由外层事务回滚，旧解析记录、正文和索引保留。同步关键词上传仍按既有分支处理。 |
| 拆书跳过、富文档批量采纳 | `book_import/reverse.py::skip_paused` 更新断点再调用继续，判定提前到断点写入前。`rich_document_review.py` 的批量采纳直接将待审核改为排队，在改动正文、版本、提案及断点前判定。 |
| 智能体提案 | 会新建后台任务的提案确认携带维护错误，事务回滚使该提案仍为待确认。整轮处理中已经提交的其它决定照实返回，剩余任务提案保留。普通确认或拒绝提交后触发的 `maybe_resume` 遇到维护时保留已提交决定和待审核任务。整轮响应沿用 `notice`。会话刷新后，如轮次仍待审核且已无未处理提案，显示「继续本轮」，使用现有任务继续接口及其身份校验，开关关闭后可继续。原有取消与适用任务的提前结束规则照常执行。 |
| 人工操作带出的可选后台工作 | 单章富文档提案可保存人工采纳结果，遇到维护以 `analysis_warning` 提示自动分析未排队。记忆编辑或撤销提案等已提交改动照常返回，作者与协作者两条人工向量派生路径停止入队。后续可由用户发起分析或索引。 |
| 运行中任务的派生 | 章节成功回调的自动分析、分析或批量分析的向量任务、拆书执行过程的分析派生，使用已有完成收据或原运行轮次与存活执行者核验。保留各自业务开关与授权复核。不会因客户端参数、`auto` 标志或同款任务类型获得放行。当前直接构造 `Task` 的路径在 `analysis_service.py` 与 `kb_index_service.py`，实施时复核每一处。 |
| API Key 开放接口 | `app/api/open/__init__.py` 已核实全部是读取与同步导出。它们沿用现有响应、限流与授权。未来创建后台任务的端点接入相同的事务检查及既有 `detail`、`code` 响应结构。 |

## 管理端的排空状态

- 新增 `GET /api/v1/admin/system-settings/drain-status`。要求 `settings.read`，返回 `no-store`。只读返回有效开关、采样时间、`queued`、`running`、`paused`、`finalizing`、活动备份数和存活进程。开关保存响应继续采用现有系统设置结构。
- 用同一主库读快照计算开关和数量。直接统计 `tasks` 的三种活动状态，不按任务监控页的筛选条件。额外统计 `task_execution_slots` 中还在占用且未被相同任务 UUID、入队与执行轮次的活动行覆盖的执行体。任务领取与占用同事务提交，引擎在成功回调、派生及收尾以后才释放占用。已确认失联的执行占用由现有接管流程清理。这样父任务已成功、子任务尚未写入时仍可见非零活动量。
- 存活判断共用 C1 规则。PostgreSQL 依据主库时钟、心跳截止时间和终止标志。SQLite 核对主库仍开放的登记及配对租约库的真实心跳，读路径不写围栏。SQLite 可在一次侧库读事务批量核验。对同一应用的 HTTP 与调度登记按内部监听身份归并，未通告地址时按主机与进程号归并供运维定位。响应仅包含主机、PID、启动时间和最近心跳，不返回内部监听地址、路径或租约密钥。
- 系统设置页沿用表单的待保存、还原和审计入口。单独刷新排空状态，复用可见轮询工具，页面可见时每 5 秒更新，保存后立即读新取样。保持草稿与观测状态独立，切账号、失权、离页废弃旧响应。读取失败或过期时清楚标记，不能从缺失数据或上次的零值判断排空完成。
- 只有开关开启且活动任务、收尾和备份都为零时显示已排空。待审核提示可人工结束或取消。有任务监控权限时提供现有任务页入口。现有详情和取消分别沿用 `tasks.read`、`tasks.cancel`。

## 整库备份及运维

计划备份到期且准备受理时，在现有备份计划写锁之前取得同一授权写屏障，读取持久开关。开启时保留现有到期时间和配置，跳过本次受理。关闭后按既有调度和同日去重规则处理到期计划。已排队、运行或恢复中的备份，以及具有备份运行权限的手动请求，沿用 C5 代码路径。管理端用 `backup_runs.active_slot` 显示活动备份，供运维确认手动快照也已完成。

README 记录开启排空、处理待审核、等待收尾与备份、手动备份和关闭排空的顺序。请求内同步 AI 调用另由运维等待完成或在停服时中断。C7 验证多 worker 部署，C8 验证升级与恢复快照。C6 的生产启动方式继续使用单个 Uvicorn worker。

## 迁移与回退

以实施时唯一 head 为准顺延，当前预期 `0070`。值仍存于稀疏 JSON 对象 `system_settings.overrides`，历史行缺少此键即采用部署基线，因此升级不需要新增列或回填。设置审计摘要的条数及类型白名单同步更新为七项。旧版读取设置和审计都严格校验 key，因此 downgrade 检查当前覆盖和 `system_settings.update` 的已存审计摘要，存在 C6 键时拒绝降级并保留数据。无该键时迁移可往返。已运行过新语义而需回退时，使用升级前整库快照和匹配的旧版本。
