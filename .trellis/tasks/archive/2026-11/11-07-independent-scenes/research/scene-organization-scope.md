# 场景组织：排序、拆分、合并与跨章移动

研究日期：2026-11-07。D4 默认继承／按项覆盖已确认，用户随后批准 D5＝章内排序、手动拆分及相邻合并，暂不跨章。本文件保留产品范围与风险依据；最终技术设计仍需审阅。

## 1. 观察与控制

作者能够显式指定场景顺序、拆分光标以及是否合并两个相邻场景。系统能观察原正文、场景身份和所有结构化引用。应利用作者的明确选择，不按空行、人物名或 AI 猜测边界。

需要保护的不只是正文：顺序决定场景时点，场景归属决定所继承的章级默认，稳定身份还连接矩阵、演变锚点和历史。

## 2. 现有合同提供的约束

- `backend/app/services/setting_progression_service.py:571`、`:583`：故事位置变更后，在原事务中重验和重算全部有效设定，不只刷新显示顺序。
- `backend/app/services/chapter_numbering.py:73`–`:103`：章号引用有统一注册表；已建章身份跟随实际 FK，删章后的孤儿不能凭同号新章复活。场景同样不能把当前显示序号当作稳定引用。
- `backend/app/services/planning_lifecycle.py:200`–`:228`：两个来源都有实质规划时先产生明确合并冲突；空单元可退役，但不能偷换身份。该模式可作为场景元数据冲突的参考，不能直接当成无需设计即可复用的场景合并实现。
- `.trellis/spec/backend/setting-progressions.md`：顺序变更需校验所有受影响历史区间，若结构化事实变得不合法则整笔拒绝；孤儿事件保留并提示，不静默删除作者历史。
- D3a 已确认：AI 不改场景结构。因此若首版允许拆并，必须是作者明确发起的人工组织操作。
- D4 已确认：场景实时继承所属章节的默认。跨章移动不仅改变位置，还可能改变未覆盖的 POV、标签和关联。

## 3. D5 已确认的首版范围

用户已批准：

1. 同章卡片／网格拖动排序，另提供键盘／移动端可用的上移、下移等非拖动方式。
2. 作者在当前场景正文的明确光标处手动拆分；不自动识别场景。未保存草稿须先受控保存或明确提示，不能拿旧服务端正文拆分而覆盖新草稿。
3. 合并同章两个相邻场景；展示正文顺序及元数据／引用影响，存在无法安全表达的冲突时要求先处理，不能静默丢弃。
4. 跨章移动暂不纳入首版。两个章节的默认联动、时间线变更和结构历史联动后续单独规划。

收益：旧章可以从一个初始场景逐步整理出真实场景，也能纠正划分，同时把首版控制在单章结构操作。代价：作者暂时不能在不同章节之间拖动场景。

未选备选：本期同时纳入跨章移动。它增加双章预览、所属章变更后的继承规则、场景演变时间变化与历史恢复等契约，不能当作拖动 UI 的一个小开关。

## 4. 拆分／合并不能自动解决所有锚点的原因

反例：相邻 A、B 两个场景之间有一个生效事件。合并后只有场景 C 的开头和结尾两个边界。把事件放到 C 开头会提前生效，放到 C 结尾会推迟生效；仅保留原 A／B 的 ID 也不等于仍有可用的中间位置。

因此，在不新增段落级／字符级时点的首版里，无法对所有合并保证原时点等价。安全设计必须采用明确预检和拒绝／作者显式重绑，不得偷偷把中间事件移到外边界，也不能为了合并成功删除事件。

同样，两个场景不同的 POV／摘要或相互冲突的规划不是可以靠集合求并自动解决的作者意图。要么让作者明确解决，要么不执行合并；正文未丢不代表合并没有丢资料。

## 5. 后续设计需落实的边界

- 重排只改变位置，身份和显式元数据不变；受影响的时间线、整章投影、提及指纹、矩阵和历史在同一逻辑提交后保持一致。
- 拆分前后原文字可逐字符重组，不因插入默认空行改变原稿；不要按 trim 后的文本计算光标。
- 普通无引用拆分可以有确定性的初始元数据规则；已有节点、交汇或演变锚点时，需要明确记录每类引用是否可无损保留。未能证明无损的情况阻止操作并列出阻塞项。
- 合并预检必须检查两方元数据、关系引用及所有需要保留的演变位置；仅检查当前激活事件不足以保护保留历史。
- 删除场景、删除最后一个场景、结构历史恢复与拆并走同一组保护原语，不能用另外的删除路径绕过预检。
- 写作任务期间的结构操作与过期预览提交应明确冲突，不允许排序改变后旧 AI 按原下标写到另一场景。
- 场景身份不复用；备份重映射和历史恢复处理真实身份，不按场景标题或当前第几个来认领旧引用。
