## Goal

给出受支持的多 worker 与多实例启动方式，保证多个实例同时启动时迁移安全，在真实多进程环境中按父任务的验收标准逐条验证，然后把 README 与规范中的「单进程」限制改写为新的前提。

## Background

- 镜像启动命令是 `alembic upgrade head && uvicorn app.main:app ...`，不带 `--workers`（`Dockerfile:37`）；`backend/alembic/env.py` 没有迁移互斥。SQLite 历史迁移存在自动提交边界，不能假定全程原子；此前没有真实多实例并发迁移记录（父任务 `research/deployment-migration-rollback-background.md` 第 4.2 节）。
- Compose 只有一个 `app` 服务，端口直接发布到宿主（`docker-compose.yml`）。
- README 第 96 行与「当前限制」写明只能单进程；部分后端规范仍沿用单进程前提（父任务 `design.md` 第 9 节列出原始清单）。
- 现成的隔离验收脚手架：`.trellis/tasks/archive/2026-11/11-18-browser-acceptance-backlog/research/harness/`（隔离 SQLite 应用与本地假模型，固定单实例、固定迁移到 head）；`backend/tests/backup_acceptance/` 的容器编排部分可参考。归档验收记录没有留下 PostgreSQL 容器的启动命令。
- `/healthz` 不检查数据库（`backend/app/main.py`）。
- 当前迁移 head 为 `0070`。两个请求／调度租约属于同一应用进程，验收进程数时需按实例与 PID 去重。[C6 验收记录](../11-20-mp-drain-switch/research/verification.md)
- 同机 SQLite 和 PostgreSQL 16 的隔离迁移预研已验证竞争与失败回滚的基本方向；正式代码、带业务数据的升级和真实部署验收仍待实施。[预研](research/migration-research.md)

## Requirements

- **R1 迁移并发保护**：多个实例同时执行启动迁移时，迁移只被执行一次，其余实例等待后正常启动；迁移失败时所有实例都不带着半完成的结构启动。失败后若后续实例从已回滚的完整旧结构重新迁移成功，可以启动；持续失败时所有实例均不得对外服务。
- **R2 多 worker 启动方式**：通过部署配置选择同一实例内的进程数，默认仍为 1；镜像与 Compose 支持该配置。
- **R3 多实例部署说明**：README 给出多实例部署的前提与配置：相同的 `JWT_SECRET` 与 `ENCRYPTION_KEY`、内部通道的通告地址与内网互通、共享 `BACKUP_DIR`、反向代理对 SSE 的要求、SQLite 只支持同机多进程。
- **R4 真实多进程验收**：提供可重复执行的验收脚本，启动真实的多个应用进程与本地假模型，在 PostgreSQL 16（同机多 worker、两个实例）与 SQLite（同机多进程）上按父任务 `prd.md` 的适用 AC 逐条执行并留下记录，包含强杀进程、断开内部通道、多实例同时启动等故障注入。
- **R5 运行参数的文档化**：租约期限、心跳间隔、轮询间隔、失联任务收尾的时间上界、崩溃后立即重启时的收尾延迟、CPU 限流器按进程计的说明写入 README 与规范。
- **R6 README 与规范收口**：README 第 96 行与「当前限制」改写；所有写明单进程前提的规范更新为新的契约，并通读确认没有遗留的「单进程」表述与新行为矛盾。
- **R7 运维操作步骤**：补充排空开关的使用、多进程下的停服顺序、同版本滚动重启的影响（被重启进程的运行中模型调用通常记为中断，已确定的业务结果按收据处理）；如 C8 已写入升级与回滚步骤则在其基础上补充，否则先写当前版本的操作步骤并保留 C8 的旧版演练范围。
- **R8 待办更新**：`TODOS.md` 第 25 项第一个待办勾选并写明验收记录与已知限制。
- **R9 单进程回归**：后端与前端全量测试、lint、构建通过。
