# 技术设计：管理员作品管理

## 1. 范围和结构

新增管理员全量列表 `/admin/projects`，打开内容继续使用 `/projects/:pid/...` 工作区与 `/projects/:pid/read/:cid?` 阅读器。现有导航、store、内容 API 及表单最大限度复用，不建立第二套编辑器。

后端只给审计过的人工内容操作增加管理员例外；严格拥有权检查保留，账户资源、任务、AI、生成日志与导入导出不随之开放。不新增依赖或数据库表。

证据见 `research/backend-admin-access.md`、`research/frontend-admin-workspace.md`、`research/verification.md`。

## 2. 授权边界

### 2.1 真实身份与统一内容授权

- 保留 `get_owned_project(db, user_id, project_id)` 和独立的 `get_owned_chapter` 严格语义。
- 增加明确命名的 `get_manageable_project(db, actor_user_id, project_id)`：所有者可访问；其他用户只有当前数据库记录为启用管理员时才可访问；其余统一 404。管理列表仍由 `AdminUser` 依赖返回明确 401/403。
- 人工内容服务使用该管理授权入口；项目内子资源仍同时约束资源 ID 与 project_id，不能因为管理员身份读取路径外的任意条目。
- 对世界观/人物/大纲工厂、章节/版本等混用 helper 的调用图逐项核查。被 AI、生成日志、任务复用的严格 helper 不得全局改义；使用新的人工入口或增加严格拥有权前置检查。
- 调用下游始终携带真实管理员 ID。项目所有者 ID 仅可用于已确认的项目关联数据规则，不能替换认证 principal、选择账户配置或创建任务。
- 不使用客户端传入的 owner ID、临时 JWT、全局 dependency override、ContextVar 冒充身份或 API 请求路径重写。

### 2.2 明确允许的内容操作

| 模块 | 允许的人工操作 | 必须保留的业务规则 |
|---|---|---|
| 项目 | 详情、资料/状态 PATCH、删除 | 校验长度与标签；拒绝跨用户 `style` / `default_style_id` 变更，保留原绑定 |
| 世界观、人物、大纲基础 | 现有 CRUD | 子资源归属与既有校验 |
| 章节、选角、版本 | CRUD、已有大纲建章、选角、版本内容查看与恢复 | 生成中锁、字数、版本事务、章节号平移；拒绝跨用户 `style_id` 变更 |
| 组织、关系、职业 | 既有人工维护、历史与图谱 | 循环检测、成员/角色/类型引用与唯一性、历史记录 |
| 大纲进阶 | 树、移动、手工细纲、建章、快照维护/恢复 | 编号约束、冲突与事务，不开放 AI 或文件导入导出 |
| 伏笔 | 既有 CRUD、状态流转、历史/统计/提醒 | 关联章节/人物归属和原有状态规则 |
| 封面 | 读取、手工上传与删除 | 格式/大小/魔数、缓存版本；生成与提示词生成仍严格归属 |
| 知识库 | 已有文档/分块读取、注入开关、删除、项目检索设置维护 | 不选择所有者 embedding 配置，不触发解析/索引/向量请求 |
| 剧情记忆 | 既有手工 CRUD、钉住/屏蔽、列表 | 自动记忆不可直接改正文/删除；更新关键词块并失效旧向量，跨用户保存不 enqueue vectors |
| 阅读 | 目录及正文 | 不读取或写入所有者阅读进度；不挂载其任务/分析订阅 |

### 2.3 严格拥有权继续控制的操作

AI 生成/润色/分析/重写/向导/批量/智能体、任务及恢复/取消、生成日志 `messages`、模型配置、平台 Key、私有模板/风格/Skill/MCP、阅读进度、导入导出/备份、知识库上传/重建/向量搜索等保持 owner-only。管理员管理自己的项目仍走正常行为。

尤其注意：剧情记忆普通 API 保存后 `_enqueue_vectors` 会按 `project.user_id` 选模型；必须仅在操作者是所有者时执行，不以隐藏按钮替代后端控制。

## 3. 接口契约

### 3.1 新增管理列表

`GET /api/v1/admin/projects`，依赖 `AdminUser`。

| 参数 | 约束与语义 |
|---|---|
| `q` | 可空，最多 200 字；去首尾空白，项目名/用户名大小写不敏感子串搜索；`%`、`_`、反斜杠按字面量 |
| `owner_user_id` | 可空正整数；限定所属用户 |
| `status` | 可空，`planning` / `writing` / `completed` |
| `page` | >=1，默认 1 |
| `page_size` | 1–100，默认 20 |

返回 `{items: AdminProjectOut[], total: int}`。

`AdminProjectOut`：`id`、`title`、`genre`、`status`、`owner_user_id`、`owner_username`、`chapter_count`、`total_words`、`created_at`、`updated_at`。所有字段具有后端 schema 与前端镜像类型。

过滤后 count 与 items 使用相同条件；Project join User + 章节分组统计；固定次数查询，避免逐行 `project_out`。顺序为 `updated_at DESC, id DESC`。沿用现有 `{detail}` 错误及 422 参数校验。不存在的 owner filter 返回空列表。

### 3.2 项目详情的归属信息

为 `ProjectOut` 增加可空的 `owner: {id, username}`（默认 null，前端兼容现有 fixture）。管理可访问的项目详情与更新/刷新路径返回正确 owner 信息；不包含邮箱、密钥、配置、全私有风格内容等。

`managingOther` 为纯派生值：当前认证用户是管理员、当前 project.id 与路由 pid 一致、服务器 owner.id 与当前用户不同。不能只凭点击来源、查询参数或可变全局标记授权。尚未拿到归属元数据时不得先挂载跨项目 AI/任务副作用。

个人 `GET /projects` 继续仅返回自己的项目；为自己的项目可返回 owner 或保持 null，但兼容分支不应意外关闭自己的既有功能。

跨用户详情投影中的 `reading` 应置 null，不查询或返回所有者的阅读进度；管理员阅读只依赖目录、章节和本地位置。不能仅由前端忽略进度来代替该响应边界。

### 3.3 内容写入与删除

使用现有内容路径、请求 schema 和中文错误，只有明确选定的操作增加管理员内容权限。跨用户项目风格字段若被提供则后端 403，前端省略该字段；其他正常资料与正文保存不受影响。

项目删除继续使用 `DELETE /projects/{project_id}`；经管理权限验证后复用原有删除与级联规则。界面要求输入准确项目名称，客户端提示后才发送请求；后端只按项目 ID 与当前真实角色授权，不把输入名称当权限凭证。删除不存在项目 404。

## 4. 前端数据流

```text
真实登录用户
  → RequireAdmin + adminApi.listProjects
  → 管理列表（搜索/所属用户/状态/分页）
  → 现有 /projects/:pid 工作区
  → projectApi.get + 服务端 owner 元数据
  → 派生管理模式、归属横幅、允许的人工模块
  → 现有内容 API + 后端逐请求内容授权
  → 保存原项目并刷新；所有者重新读取可见
```

- 新 `AdminProjectsPage` 懒加载，沿用 AntD、memo loader、统一 ApiError、时间格式与主题 token。所属用户筛选复用已有管理员用户搜索，不一次拉取全站用户。
- `AppLayout` 账户菜单、全局侧栏、当前页面名称及管理工作区返回链接同步增加作品管理入口。
- 共享的管理能力派生逻辑绑定当前 project.id 与 user.id；需要在 ProjectLayout 外的 Reader 使用同一语义，不另建可变的当前所有者状态。
- 管理模式不挂载 AgentDock、批量任务轮询/横幅、编辑器任务接续、`useChapterAnalysis` 请求与订阅、生成日志标签、向导和所有者资源操作。需要 enabled 的 hooks 在 effect 与 action 两层一起拦截，不能仅隐藏 DOM。
- 私有风格控件改为显示已引用摘要；概览保存不发 default_style_id，章节保存不发 style_id，避免既有表单默认值把绑定清空或误换成管理员资源。
- Reader 管理模式不采用 `project.reading` 作恢复位置，并关闭常规/keepalive/unload 进度上报。直接链接、刷新、切章均保持归属提示。
- 快速切换项目时只接受当前目标 load/refresh 响应，避免旧 owner 与新内容混用；401/登出遵循现有用户 store 重置。

## 5. 兼容、风险与回滚

- 无迁移、无新依赖、无多管理员角色体系；原有 API 字段只增加可空 owner，普通用户隔离与自己的项目工作流保留。
- 主要风险为混用 helper 放开 AI/日志、记忆索引隐性调用、私有风格引用误写、Reader 修改他人进度，以及管理身份缓存串项目；分别纳入后端隔离/副作用测试与前端网络验收。
- 编辑沿用现有保存与并发限制，不新增多人编辑合并；管理员与所有者可覆盖对方近期修改的既有风险在交付说明中明确。
- 删除仍遵守现有任务级联语义；已发出的外部模型请求无法通过删除数据撤回，不承诺删除立即终止已发生的调用。
- 发布时前后端一起更新。回滚本任务代码即可恢复旧权限与入口；已经保存的内容修改和确认删除的数据不会随代码回滚恢复。

## 6. 方案取舍

独立 `/admin/projects/:pid` 编辑/API 命名空间能表达管理路径，但现有导航、API、Reader 及 store 有大量普通路径耦合；为该功能全面改写会扩大范围。继续使用原内容路径、严格 helper 与人工 helper 分离，可复用业务规则并让跨用户权限集中审计。

不采用整个 router 复制并替换 user.id，也不进行全项目 `Actor` 参数大重构。后续若需要协作角色、所有权转移或操作审计，应另行设计。
