# 作品回收站技术设计

状态：2026-10-31 用户已明确批准最终方案，任务已激活并进入实施/独立检查。本文是实施基线，不单凭文档宣称检查通过；实际结果以 verification 和 research 报告为准。需求以 `prd.md` 的 R1–R8、AC1–AC8 为准。

## 1. 边界与模块

沿用 FastAPI → service → SQLAlchemy 的现有分层，不引入独立队列、通用软删除框架或新的前端组件库。

- `project_service.py`：保留普通作品 API 的入口和拥有权/人工管理语义；DELETE 改为调用回收站协调器，并显式接收任务引擎。
- 新增轻量 `project_lifecycle.py`：只依赖模型、数据库和错误类型，集中定义正常项目条件、可写项目事务锁、UTC 生命周期判断；避免 `project_service` 与任务服务循环导入。
- 新增 `recycle_bin_service.py`：删除协调、管理员列表/恢复/彻底删除、到期清理和遗留删除意图恢复；复用现有任务取消与审计设施。
- 新增 `api/v1/admin_recycle_bin.py`、`schemas/recycle_bin.py`；全部回收站路由使用 `AdminUser`，普通 DELETE 仍使用真实 `CurrentUser`。
- 前端新增 `AdminRecycleBinPage`、独立 API 模块及必要的小型确认组件；复用 AntD、`RequireAdmin`、`useLoader`、时间与名称确认工具。

## 2. 持久化状态与迁移

在实施时确认最新 Alembic head；以当前 `0023` 为父新增 `0024_project_recycle_bin`，不修改已发布迁移。

`projects` 增加下列可空列，存量项目保持正常：

| 列 | 含义 |
|---|---|
| `deleted_at` | 成功进入回收站的 UTC 时间；非空即为回收站作品 |
| `last_deleted_at` | 内部删除时间高水位，恢复后仍保留，防止冻结/回拨时钟复用公开代次 |
| `deleted_by_user_id` / `deleted_by_username` | 删除者快照，无业务外键，不因操作者之后删号丢失 |
| `deletion_started_at` | 正在停止任务的删除意图时间，尚不是已删除 |
| `deletion_token` | 本次协调操作 UUID；后续提交/撤销仅能处理自己持有的意图 |

- 增加 `(deleted_at, id)` 清理索引及状态一致性约束：已删除状态不与删除中状态并存，意图时间与 token 成对出现。
- SQLite projects 启用 AUTOINCREMENT，防止最高ID作品purge后被同名新作品复用；PostgreSQL沿用原序列。不只保证同实体的时间高水位，还要保证跨实体ID不复用，才能让 `(project_id, deleted_at)` 在冻结/回拨时钟下仍唯一识别删除代次。
- 不向 `projects.status` 添加 `deleted`，它仍表示创作状态；到期时间由 `deleted_at + timedelta(days=30)` 计算，不另存可能漂移的副本。
- 最终软删除在父行锁内生成 `stamp=max(now_utc, last_deleted_at+1微秒)`，同事务写入 deleted_at/last_deleted_at；恢复只清当前删除标记，不清高水位。正常时钟下等于当前UTC，冻结/回拨时使用单调逻辑UTC，确保旧页面永远不能因时间值重复命中新代次；高水位同样不导出/不接受导入。
- `projects.user_id` 外键从 `CASCADE` 改为命名的 `RESTRICT`，防止绕过服务或并发创建作品时由删号级联毁掉作品；项目向下的 CASCADE/SET NULL 不变。
- 为系统清理留痕，将 `admin_audit_logs.actor_user_id` 改为可空，既有数据原样保留；仅内部系统清理记录使用空 ID 和明确系统名称，不构造用户 0 或冒用删除者。
- PostgreSQL 使用真实约束变更；SQLite batch 迁移必须用存量父子数据验证不会因重建 `projects` 导致子表级联丢失，并做外键完整性检查。不能只测空库。

正常查询条件统一为 `deleted_at IS NULL AND deletion_started_at IS NULL`；仅回收站服务和内部取消收尾可访问其他生命周期状态。

## 3. 删除状态机与安全性

```text
正常 → 删除中（提交准入屏障）→ 停止任务并等待执行体/收尾 → 回收站
                └─ 失败/超时/请求取消 → 正常（已取消任务不回滚）
回收站且未到期 → 管理员恢复 → 正常
回收站 → 管理员彻底删除 / 到期系统清理 → 物理删除
```

### 3.1 先冻结准入，后等待任务

1. 按真实 actor 校验所有者或当前启用管理员权限。锁定正常父项目，写入本次 `deletion_started_at/token` 并提交。
2. 提交屏障后新建、重试、继续、自动分析/索引排队和普通项目写入均拒绝；不能只“先查活动任务再删除”。并发第二次删除返回冲突，不复用另一操作的 token。
3. 仅内部按该项目范围取消所有 `OPEN_TASK_STATUSES`。从现有 `cancel_task` 抽取复用按已核实 Task 执行的取消逻辑，不通过把 actor 换成 owner 来调用他人接口，也不新增通用管理员任务权限。
4. 以统一有界 deadline 等待执行体、`_finalizing`、`on_abort` 与 `on_success` 真正退出。既有 `cancel_running` 等待返回、任务已为终态或查不到 queued/running 都不单独构成安全证明。
5. 在新事务内按 token 锁定父项目并重新读取 actor 权限；复查不存在未结束任务和执行中/收尾中的关联工作。记录当下 `deleted_at`、删除者快照，清除意图，和成功审计同事务提交。
6. 失败或超时时只清除属于该 token 的意图，作品保留；已取消的任务和已保存的内容不倒退。清除意图前回滚失效事务，不提交半成品内容。

不得跨等待持有项目行锁，否则取消/成功回调可能等待同一行造成死锁。准入屏障是已提交状态，而不是长期未提交锁。

### 3.2 任务运行与收尾登记

- 扩展引擎的内部执行登记，使项目协调器能识别“数据库状态已结束，但执行体/成功回调仍在运行”的任务。
- 排队、待审核任务的取消清理也必须纳入登记，避免另一个取消请求已先置终态、但 `on_abort` 仍在写项目的竞态。
- 运行任务在完成事件后可能已成功/暂停而不再接受 cancel；允许其正常收尾，但仍等待所有回调退出并禁止派生任务。
- 既有吞掉 `on_abort` 异常的 handler 不能让删除协调器误判成功：需反馈失败或验证可恢复的资源状态，无法证明收尾完成就拒绝移入回收站。
- 调度器领取时也过滤非正常项目，避免已删除/删除中项目因遗留 queued 任务再次运行。已进入执行体的任务通过已有取消/finally 收尾。
- 进程崩溃后，下一次单进程启动先恢复未完成删除意图，再由任务引擎按既有规则把遗留 running 收尾为 interrupted；不自动完成上一次未成功的删除。
- 正常退出或请求取消必须用可靠 finally 清理本次意图；不能让一次断网永久锁死作品。若数据库当时不可用，启动恢复负责解除遗留状态。

### 3.3 普通写入的事务屏障

只过滤读取不够：已通过权限校验的请求可能在删除后才提交内容。

- 为拥有权和人工管理 helper 增加显式的写锁选项；修改入口在同一写事务开始时获取父项目锁并重读生命周期状态，直到本次业务提交/回滚才释放。只读入口保持无写锁。
- 复用 `agent/tools/base.py::lock_project` 已有的条件 no-op UPDATE 思路：显式保留 `updated_at`，集中加入正常生命周期条件，兼容 PostgreSQL 和 SQLite 的物理事务；不为每个模块复制锁逻辑。
- 覆盖正文/版本、设定/关系/组织/职业/伏笔、大纲/快照、封面、知识库/记忆、阅读进度、灵感应用、智能体提案/撤销、分析回写和任务准入。多次提交或换 session 的入口必须在每次后续项目写入前重新获取屏障。
- 任务创建在校验/抢占与插入 Task 的同一事务内持有父项目锁；不能先单独提交章节抢占再检查生命周期。重试、继续和自动 enqueue 走相同准入条件。
- 删除屏障若先取得锁，后来的写入读到删除中并失败；普通写入若先取得锁，删除必须等待其提交后才建立屏障。因此不存在已授权旧请求穿过屏障提交内容的间隙。
- 对已有任务取消/finally 的受控收尾保留必要写入能力，等待这些工作结束后才进入回收站；这不是可通过 HTTP 打开的 `allow_deleted` 权限。

## 4. 查询与访问覆盖

不能使用隐藏的全局 ORM 过滤器掩盖漏查。集中 predicate + 现有授权 helper 为主，显式覆盖绕过 helper 的查询：

| 消费方 | 处理 |
|---|---|
| 个人书架、管理员正常作品目录、对应 count | 排除回收站和删除中项目，count 与 items 同条件 |
| 项目/章节直接 ID、分析回写 ID | 父项目生命周期与原拥有权同时校验，保持跨用户 404 |
| 开放 API 小说列表、`get_authorized_project`、封面与下载 | 即便 Key 原有授权还在也不能访问回收站；不扩大 Key 范围 |
| Task 全局列表、详情、输出、SSE、重试/继续/删除/清空/裁剪 | 不暴露回收站项目内容；隐藏的历史 Task 不因普通全局清理而破坏恢复数据，既有有界历史裁剪需排除回收站作品 |
| AI/智能体/知识库任务、生成日志、分析、记忆和向量 | 入口和提交/自动排队点均检查；删除协调等待真实执行链退出 |
| 灵感会话、备份流生成器等直接 `db.get(Project)` | 按生命周期判断关联作品是否可用，不用保留下来的行绕过访问限制 |
| 风格等用户资源的引用计数 | 仍需计入回收站的真实引用以避免悬空，不把它误作正常书架统计 |

回收站只展示必要元数据，不提供正文编辑工作区。新发起的普通访问：回收站项目为 404；已授权的删除中项目可返回 409；第三人仍为 404。已发送至客户端的字节或缓存不可撤回。

KeyInfo及密钥管理仅投影正常作品ID，底层grant保留。为避免隐藏投影破坏原密钥编辑，前端区分创建与PATCH：创建仍至少选择一部；编辑的可见范围按all_projects和ID集合比较，未变时省略范围字段，即使投影[]也允许仅改名/有效期；明确改范围才按当前选择完整替换。表单必须说明未改范围会保留暂不可见授权，不能把整表提交误作用户撤销隐藏授权。

## 5. 回收站 API 与前端契约

前缀：`/api/v1/admin/recycle-bin/projects`。

| 方法/路径 | 输入 | 成功 |
|---|---|---|
| GET `/`（实际注册空子路径） | `q?` ≤200、`owner_user_id? >0`、`page=1`、`page_size=20`（1–100） | `{items: RecycleProjectOut[], total}` |
| POST `/{id}/restore` | `{deleted_at: AwareDatetime, confirm: true}` | 204 |
| POST `/{id}/purge` | `{deleted_at: AwareDatetime, title: string, confirm: true}` | 204 |

`RecycleProjectOut` 包含 `id/title/genre/status`、`owner_user_id/owner_username`、删除人快照、`deleted_at/expires_at/restorable`、章节数/总字数；不加载封面二进制或正文。聚合复用 `chapter_stats_subquery`，按 `deleted_at DESC, id DESC` 排序；搜索沿用大小写不敏感、LIKE 特殊字符按字面量转义。

- `deleted_at` 是服务端回收站记录代次，由持久 last_deleted_at 保证不复用：前端原样回传，不能经 JS Date 截断微秒。服务端归一化 UTC 后锁行比较，防止“恢复→再次删除”后的旧页面误操作新记录；不能假定真实时钟一定产生不同值。
- `confirm` 必须为真正 JSON boolean true；彻底删除名称与服务器当前标题逐字相同，不 trim 宽松放行。
- 未登录 401；非管理员 403；不存在/已物理清理 404；非回收站目标、记录代次变化、超期恢复为 409；名称不符 400；非法参数 422。恢复已恢复目标返回明确冲突，而非再次修改时间或写重复成功日志。
- 原 `DELETE /projects/{id}` 保持 204 成功外形；取消/收尾超时返回带稳定 code 的 409，提示作品未删除和已取消任务不会自动恢复。
- 管理端页面采用懒加载 `RequireAdmin` 路由 `/admin/recycle-bin`，同步桌面/移动导航和页名。表格/窄屏卡片展示到期时间、可恢复/已到期待清理状态；已过期记录不能恢复。
- 恢复普通确认；彻底删除使用危险色、明确不可恢复说明和完整名称输入。忙碌时防重复提交和切换目标；失败显示原因，不提前从列表移除。
- 搜索/归属/页码变化使旧加载响应失效；操作成功重新读取列表，末页删空回到有效页。跨登出、角色变更、弹窗切换不得接受旧操作响应影响新目标。
- 所有作品删除入口说明 30 天和管理员恢复；复用现有名称确认组件，不新增三套删除逻辑。用户管理 `project_count` 继续包含全部未物理删除作品，标签注明含回收站；有作品时给出禁用及处理作品的入口，服务器仍是最终裁决者。

## 6. 恢复、彻底删除与保留期

- 所有时间取统一服务端 UTC；30 天为连续 `30 × 24` 小时。`now < expires_at` 才可恢复，等于或大于即不可恢复。
- 恢复与 purge/expire 均在锁定目标行后重新校验本次 `deleted_at`、期限和状态；只有一个操作能成功。恢复清空删除元数据，保留内容、ID、owner 和创作状态，不触发任何模型或向量重建。
- 上述“清空删除元数据”不包括内部 last_deleted_at 高水位；它跨恢复、独立session及进程重启保留。普通内容往返比对需单独排除并验证该生命周期字段。
- 所有者禁用不阻止管理员恢复，但不改变账号状态；所有者缺失属于异常数据，拒绝恢复并提示，不创建账户或迁移归属。
- 封面等项目级数据软删除时原位保留；独立用户资源遵守既有删除/SET NULL/回退规则，不重建不存在的私人资源；现存 Key 授权在恢复后按原规则再次可用。
- 彻底删除前确认无执行中/收尾工作，然后用既有项目向下外键清理，灵感会话按 SET NULL 保留；不要把备份注册表误当成完整清理清单，因为 tasks/agent/检索等本就不导出。
- 清理成功后失效对应项目检索矩阵缓存、任务 hub 和前端项目/任务状态，防止 SQLite ID 重用或旧异步响应带来内容串用；恢复也使相关派生缓存失效。

## 7. 自动清理与可恢复失败

- 不引入第三方调度器。生命周期内启动可等待停止的清理协程：启动补清一次，持续运行每小时一次；测试使用可注入时钟/间隔、显式 start/stop。
- 一次清理固定 UTC 截止时间，按 `(deleted_at, id)` 键集分批处理（每批至多 100），每个作品独立事务重读条件并删除；失败项本轮跳过，下一轮重试，不能死循环或影响其他作品。
- 恢复/手动 purge 与后台清理共用单作品核心事务；清理前锁行重新核实 `expires_at <= cutoff`，不使用事务外缓存的“已过期”结论。
- 若发现不符合不变量的活动任务，跳过物理清理并记录安全错误，不拿外键级联替代取消。标准日志不带正文、模型参数或密钥。
- 应用 shutdown 先停止并等待清理，再停止任务引擎，最后关闭数据库；不遗留 fire-and-forget 数据库任务。

## 8. 删号、审计与备份兼容

### 删号

在既有用户护栏内锁定目标用户，对其全部 Project 计数（不加正常项目过滤）；非零返回 409 和安全结构化计数，数据不变。清零后才删除用户；数据库 RESTRICT 是并发和未来漏查的最终护栏，相关约束异常只翻译为已核实的业务冲突，不笼统捕获所有 IntegrityError。

### 审计

- 既有 `project.delete` 新记录标明软删除，旧永久删除历史不改写；普通自主删除仍不扩大现有管理员审计范围。
- 增加 `project.restore`、`project.purge`、`project.expire`，以及有界生命周期摘要/计数。恢复/手动彻底删除是明确管理员动作，即使目标是管理员自己的作品也应记录；用显式局部选项扩展 writer，不全局取消现有“本人内容不记管理员审计”的边界。
- 系统 expire 使用独立内部可信入口构建系统 actor，HTTP 无法传入或伪造此身份。业务和成功日志同事务；失败先回滚再按安全白名单留痕，不保存正文、提示词、凭据或原始 SQL 参数。
- 同步后端 Literal、前端类型/标签/空 actor 展示和测试；原有日期预览/nonce/高水位清理保护不变。

### 备份

新生命周期列列入 `PROJECT_RULE.exclude`，导出不携带、导入总是生成正常项目；恶意备份不能注入删除标记、删除者或协调 token。项目备份格式仍为 v1，更新 `APP_SCHEMA` 至本次真实 head；旧备份仍可导入。启动导出后的独立流会话必须重新校验生命周期，不能因数据仍存在而导出回收站内容。

## 9. 验证与发布/回滚

详见 `implement.md` 的检查清单。核心验证包括带子数据迁移、全入口隔离、关联数据往返、所有任务状态/回调竞态、超期边界、系统审计与真实浏览器操作。SQLite 不证明 PostgreSQL 行锁正确；数据库并发与约束必须另外用临时 PostgreSQL 或明确记录尚未实测的缺口，不能声称已经证明生产并发安全。

发布前停写并备份，迁移后再启新应用，先小数据集验证无正常作品进入清理范围。自动清理只认明确非空的 `deleted_at`，不按旧 updated_at 推断删除。
