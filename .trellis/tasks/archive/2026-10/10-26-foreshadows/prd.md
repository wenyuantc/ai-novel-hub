# 伏笔管理（P0-4b）

> 父任务：`10-23-mumu-parity`，对应差距项 B6。这部分原属 `analysis-memory`，用户决定拆出来单独做，紧接其后完成（analysis-memory D1）。
> 依赖：已归档的 `analysis-memory`，用到其中三部分：伏笔候选 `chapter_analyses.foreshadow_candidates`、回写清单 `analysis_changes`（自动写入、待确认、撤销、确认、拒绝），以及分析提示词。另外依赖 `story-entities` 的角色表。
> 技术设计见 `design.md`，执行计划见 `implement.md`。

## Goal

作者可以系统地管理伏笔：计划在哪一章埋、实际在哪一章埋下、计划在哪一章回收、是否已经回收。章节分析会自动识别埋设和回收。生成章节时，模型会收到提醒：本章该埋什么、该回收什么、哪些已经超期，以及哪些长线伏笔还没收。长篇里的线索因此不会被遗忘。

## Background（代码证据）

- 分析提示词已经要求输出 `foreshadows: [{action: plant|resolve, text, keyword, expected_resolve_chapter}]`（`backend/app/ai/prompts/analysis.py:35`）。规范化后原样存进 `chapter_analyses.foreshadow_candidates`（`analysis_service.py:313,710`），目前没有任何地方使用这些数据。
- 回写清单按条目类型分发：`PENDING_KINDS = ("life_status", "relationship_create")`，另有撤销 `revert_change` 和确认 `confirm_change`，并支持"更晚章节优先"（`backend/app/services/writeback_service.py:45,382,455`）。`build_analysis_messages` 的参数里目前没有伏笔。
- `context_builder` 的段落顺序是：世界观 → 本章涉及角色 → 人物关系 → 相关组织 → 职业体系 → 名单 → 当前卷大纲 → 前情提要 → 最近正文（`context_builder.py:92-111`）。
- MuMu 的做法（`../10-23-mumu-parity/research/mumu-story-settings.md` §6）：
  - 字段多达近 20 个，其中不少在上下文里没用上，例如 `include_in_context`。
  - 关联角色存的是角色名，角色改名后关联就失效。
  - 伏笔数据有两套，彼此不同步。
  - 长线伏笔和待埋伏笔都不会被提醒。
  - ID 无效时直接跳过，不给任何提示。

## Key Decisions

- **D1（用户确认）**：分析识别出的伏笔，按可靠程度分三种处理，全部走现有的 `analysis_changes` 回写清单：
  - 回收已有伏笔（按编号匹配）：自动写入，可以撤销。编号对不上时只提示，不写入。
  - 新埋下的伏笔：进入待确认。确认时可以修改字段，确认之后才创建。
  - 计划中的待埋伏笔在本章被埋下（按编号匹配）：自动标为已埋，记录实际埋设章节，可以撤销。
- **D2（用户确认）**：章节上下文新增【伏笔提醒】段，分档如下：
  - 本章计划埋设：全部列出，附埋法要点。
  - 本章必须回收：全部列出，附回收要点。
  - 超期未回收：最多 3 条，最超期的排在前面，并标注已超期几章。
  - 未来 3 章内到期：最多 3 条，提示"可适当铺垫"。
  - 没有计划回收章节的长线伏笔：按重要度最多 3 条，每条一行简述。

  每条伏笔都有"注入上下文"开关，默认开启。预算紧张时，先裁长线伏笔，再裁即将到期的。
- **D3（用户确认）**：字段采用精简集：
  - 标题、内容、埋法要点、回收要点
  - 状态：待埋、已埋、已回收、部分回收、已废弃
  - 计划埋设章、实际埋设章、计划回收章、实际回收章
  - 重要度（1–5）
  - 关联角色：关联到角色表，删除角色时只解除关联
  - 注入上下文开关
  - 备注

  没有计划回收章即视为长线伏笔，不另设字段。不做分类、隐藏度、伏笔链、标签。

## Requirements

- **R1 伏笔增删改查**（D3）：
  - 手动创建伏笔，可以是待埋或已埋状态。编辑、删除都支持。
  - 状态流转：待埋 → 已埋 → 已回收 / 部分回收；任何状态都可以改成已废弃，也可以手动改回其他状态。
  - 章节号可以填写尚未创建的章节，表示"计划在第 N 章"。
  - 关联角色必须属于本项目。
- **R2 分析联动**（D1）：
  - 分析时，把"已埋未回收"和"计划在本章或更早埋设的待埋"伏笔连同编号交给模型。模型回收或埋下这些伏笔时，必须引用编号。
  - 分析产出的三类条目都进入回写清单：自动回收、自动标已埋、新埋设待确认。它们和现有条目一起展示，也支持撤销、确认（可修改字段）和拒绝。
  - 确认新埋设时，如果同一章已有同名伏笔，拒绝确认，避免重复分析造成重复创建。
  - 回收伏笔也遵循"更晚章节优先"：已经由更晚的章节回收过的，不再重复回收。
- **R3 上下文提醒**（D2）：在 `context_builder` 中生成【伏笔提醒】段，只取"注入上下文"开启、且状态不是已回收或已废弃的伏笔。这一段排在"前情提要"之前，裁剪顺序按 D2。
- **R4 伏笔页面**：项目导航新增"伏笔"页，包括：
  - 统计：各状态的数量、超期数量。
  - 列表：可以按状态、超期、长线、关联角色筛选，按计划回收章或重要度排序。
  - 时间线：按章节展示各伏笔"埋设 → 回收"的跨度，并标出超期的。
  - 快捷操作：标记已埋（选章节）、标记回收（选章节，可选部分回收）、废弃。
  - 关联角色的角色卡里，也能看到与该角色相关的伏笔。
- **R5 编辑器**：章节编辑器的分析面板显示本章新识别的伏笔。另外加一个轻量入口"本章伏笔"，查看本章计划埋设和必须回收的伏笔。
- **R6 安全**：所有伏笔接口都校验项目归属，非所有者访问一律返回 404；关联角色不能跨项目。

## Acceptance Criteria

- [ ] **AC1（R1/D3）**：新建一条"第 3 章埋、第 8 章回收"的伏笔，并关联两个角色，可以编辑、改状态、删除。删除其中一个角色后，伏笔保留，只解除与该角色的关联。关联其他项目的角色时返回 400。
- [ ] **AC2（R2/D1 回收）**：已埋的伏笔 #5 被第 8 章分析以编号回收后，自动变为已回收，实际回收章为 8，回写清单里能看到这条并可以撤销，撤销后恢复为已埋。编号无效时只出现一条提示，伏笔不变。
- [ ] **AC3（R2/D1 埋设）**：计划在第 3 章埋的待埋伏笔，被第 3 章分析以编号识别后，自动变为已埋，实际埋设章为 3。新识别的伏笔进入待确认，确认时修改标题后才创建；同一章重复确认同名伏笔被拒绝。
- [ ] **AC4（R3/D2）**：生成第 8 章时，提示词里的【伏笔提醒】依次包含：本章计划埋设的、本章必须回收的（附回收要点）、超期的（最多 3 条，标注超期章数）、未来 3 章到期的（最多 3 条）、长线的（按重要度最多 3 条）。关闭"注入上下文"的、已回收的、已废弃的都不出现。预算很紧时，先去掉长线，再去掉即将到期。
- [ ] **AC5（R4）**：伏笔页的统计、筛选、排序和时间线都正确，超期的有醒目标识，快捷操作可用。
- [ ] **AC6（R6）**：其他用户访问伏笔接口一律返回 404。
- [ ] **AC7（质量）**：后端 ruff 和 pytest、前端 lint、test、build 全部通过，每个 chunk 都小于 1500 kB。原有的分析、回写、上下文测试的覆盖没有减少，spec 已同步更新。

## Out of Scope

- 伏笔之间的关联（伏笔链）、分类、隐藏度、标签（D3）。
- 在正文里高亮伏笔的位置。
- 自动废弃长期未回收的伏笔。
