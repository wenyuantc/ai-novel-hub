# PostgreSQL 恢复到新库的隔离验证

在只含虚构数据的 PostgreSQL 16 容器中执行：

```sh
cd backend
python3 tests/c7_pg_restore_fresh_smoke.py
```

脚本使用随机凭据和唯一容器名及标签，数据库容器为 `--network none`，数据目录为 tmpfs，无 Docker 卷；就绪检查明确走 TCP。测试备份和环境文件仅存在于本轮私有临时目录，结束后只清理本轮容器和临时文件，没有读取项目 `.env` 或访问已有数据库。

## 结果

- 假定应用已停：该测试没有启动应用，快照前确认源测试库没有其他连接；没有演练真实应用停服。
- 对包含虚构用户、作品和 `alembic_version=0070` 的源测试库生成 custom 格式备份；随后修改源库数据并增加快照以外的表，作为保留原库的对照。
- 用 `template0` 创建先前不存在的新库，成功后使用下述 `pg_restore` 参数恢复。新库版本与快照时的虚构业务数据一致，快照外新表不在新库，源库仍保留修改后的数据和新表。
- 目标库已存在时，`createdb` 返回非零，脚本未执行 restore；已有目标库的标记数据和源库均不变。
- 另在新建目标库注入冲突，使 `pg_restore --exit-on-error` 在已执行部分 DDL 后退出非零；源库不变。失败目标库可能不完整，不得将它接入应用。

## 命令边界

完成停服、确认快照与原库状态，并事先配置连接地址、端口和认证后，可以使用以下命令门控；第二条只在新库创建成功时执行：

```sh
: "${NEW_DB:?请设置新数据库名}"
: "${SNAPSHOT:?请设置快照路径}"
createdb --maintenance-db=postgres --template=template0 -- "$NEW_DB" &&
pg_restore --exit-on-error --no-owner --no-privileges --dbname="$NEW_DB" "$SNAPSHOT"
```

成功退出仍须核对迁移版本、关键业务数据及环境，然后才考虑切换应用连接。创建或恢复失败时停止流程，不自动覆盖原库，也不把可能部分恢复的新库视为可用。

本次仅验证虚构的最小表结构和数据，并未验证完整应用恢复、实际停服或切流。`--no-owner --no-privileges` 不恢复原所有者和 ACL，恢复账号对目标库、扩展和对象的权限须另行准备；数据库编码、locale、排序规则、扩展、角色和其他集群级设置也须根据实际备份核验。跨主机、网络故障和进程强杀期间的恢复行为未覆盖。
