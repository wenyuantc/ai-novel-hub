### D-3 预期调整

复现：作者与编辑者各开一个浏览器上下文；编辑者打开项目智能体、新建会话、在输入框输入「把第 3 章标题改成「茶棚夜话」」；作者 `PATCH /projects/1/collaborators/3 {role: "viewer"}`；编辑者不刷新，点「发送」。

实际：请求 409，错误条「协作授权已变化，请重新发起」，会话转为「此会话仅供查看」。输入区由 `frontend/src/components/agent/AgentConversationView.tsx:99`（`{!historySealed && writable && (`）在不可写时整体不渲染；作品授权版本变化还会让 `AgentDock` 以新 key 重新挂载（`frontend/src/pages/project/ProjectLayout.tsx:62`，key 含 `authorizationVersion`），`input` 状态因此丢失。

判断：更可能是**场景表预期本身不准确**。E4i-h 要保证的是「被拒绝时不按已受理清空」，这一点成立（`send` 返回 `accepted=false`，没有走清空分支）；但被降为查看者后，按现有设计不可写会话不提供输入区，「输入保留」在界面上本来就无法呈现。若希望降级后仍能看到或复制刚写的内容，需要改只读态的界面设计（例如只读时仍显示禁用的输入框），这超出单点修复，按 R4 不应在本任务自行决定。**用户 2026-11-19 决定**：预期改为「请求被拒、提示授权变化并进入只读，输入区随只读移除」，D-3 按此记为通过。「降级时保留未发送草稿」不作为本任务缺陷，也不立 TODOS 条目。

### D-extra：项目智能体输入框找不到 `textbox` 角色

查明原因：输入框是包在 AntD `AutoComplete` 里的 `Input.TextArea`（`frontend/src/components/agent/AgentConversationView.tsx:108-118`），AutoComplete（rc-select）把自己的组合框属性注入子元素，实际 DOM 为 `<textarea aria-label="发给项目智能体的消息" role="combobox" aria-autocomplete="list" aria-haspopup="listbox" aria-expanded="false" type="search" …>`。Chrome 可访问树（CDP `Accessibility.getFullAXTree`）里它是 `combobox`，名称「发给项目智能体的消息」，`editable=plaintext`、`focusable`、`autocomplete=list`、`hasPopup=listbox`；`ariaSnapshot` 为 `- combobox "发给项目智能体的消息"`。所以 `getByRole('textbox', { name })` 计数为 0，`getByRole('combobox', { name })` 计数为 1。

结论：**不是可访问性缺陷**。元素有正确的可访问名称、可聚焦、可编辑，并按 ARIA 1.2 组合框模式声明了它弹出的触发词候选列表，读屏软件会把它报为可编辑的组合框，这符合它的实际行为（输入 `/` 时弹出候选）。小瑕疵：组合框角色下多行属性不被表达（`aria-multiline` 不适用于 combobox），以及 textarea 上的 `type="search"` 属性无意义；两者都来自 AntD 组件本身，影响可忽略。处理建议：harness README 里「原因未查」一句可更新为改用 `getByRole('combobox', { name: '发给项目智能体的消息' })` 定位。本批脚本仍用 `textarea[aria-label=…]`。

### G4 附带观察（不影响结论，供后续排查）

1. **会话详情接口在轮次进行中会短暂返回 404「智能体轮次不存在」**。压测：作者和编辑者各发 6 轮消息，在轮次进行中持续轮询 `GET /projects/1/agent/conversations/{cid}`，作者 45 次中 9 次、编辑者 55 次中 11 次返回 404，轮次结束后恢复 200。来源是个人投影对轮次快照的核对（`backend/app/services/personal_projection.py:646-652`，轮次状态或进度在读取期间变化时证据对不上即抛 404）。前端把会话读取 404 视为失去访问（`frontend/src/api/agent.ts` 的 `isAgentAccessLost`，受理后重读失败会交给失败处理，`frontend/src/components/agent/useAgentConversation.ts:134-155`）。本批浏览器里页面自身的读取在 34 次发送中（D-1、D-2 各 5 次，另外编辑者、作者各 12 次）一次也没撞上 404，界面也没有出现任何权限变化或错误提示，因为页面只在受理后和轮次结束时读取，而 404 出现在轮次中途。它和 E4i-h 问题 1 未查明的根因（偶发「作品权限已变化」）可能有关，但本次没有在界面上复现，按「较大问题待排查」记录，不归入 D 场景结论。
2. 编辑者（协作者）一侧，服务端轮次进入待确认后，时间线约 2.3–2.5 秒才出现工具步骤与提案卡片，期间状态栏显示「生成中」；作者一侧几乎即时（约 3 毫秒）。出现后的状态都正确（「完成」「处理中」，作废后「已停止」）。推测协作者走轮询而非实时订阅，属设计内的延迟，未判为缺陷。
