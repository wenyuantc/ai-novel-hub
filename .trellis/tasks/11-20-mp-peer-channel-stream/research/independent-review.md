# C4 设计独立复核

日期为 2026-11-24。复核范围是父任务 D2、C4 的 R1–R9 和 AC1–AC10。核对对象为需求、技术设计、实施清单、三份专题研究及 `aabd3c3` 基线的实际发送、领取和收尾代码。以下是规划阶段的审查结论，双进程功能和时限仍需实施后实测。

## 已核实的设计边界

- PostgreSQL 的基本锁序和 SQLite 两种日志模式在 `stream_lease.py:196` 实现。成员读取位于 `:261`；业务成员写入经过项目门禁，若要求直接更改数据库成员字段也与 ASGI send 串行，应在同一既定锁序中共享锁定成员行并在 PostgreSQL 竞争测试里验证。不能将 SQLite 回滚日志模式下的 SHARED 保护直接等同于 WAL 的保护。受控发送要覆盖 A 验证后、B 尚未送出时的撤权，也要验证 B 已持锁时另一个撤权写事务只能稍后提交。套接字中已经交付的字节有传输延迟，服务端的判据是提交与实际发送的先后。
- `stream_evidence.py:718` 验证本地来源、项目可见性戳和不同来源的特定约束，`:227` 对智能体提案另作任务、会话与变更身份核对。B 的有限字段描述应被限制为只读条件，由 B 按本地事件及任务类型确定必填项。任何发布、执行或写屏障都不能从这份描述重造。原来源核实、合法后继、持久终态是三种不同的依据。两端只在库锁外重核处于合法推进窗口的同一帧。没有证明的运行中协作正文应受控关闭。
- `engine.py:615` 的 HTTP request worker 可接管已受理取消的轮次，但没有模型执行现场。任务行上还在登记一个存活 worker、已有通道、或只有相同 task ID 都不能作为原发布者的证据。`engine.py:728,1868` 分别展示了持久待核对状态与本地记忆。活动读取需按精确轮次核实已知收据；未知结果应保留已有语义。强杀专项使用能证明中断的任务，另测已有成功/暂停收据。
- `engine.py:2057` 在另一个事件到来时才触发旧节流写入，尾沿写入可解决“一个 delta 后长期静默”。实施须保持 `engine.py:2065`、`handlers/batch.py:221` 的原执行/原作业/已确认文本检查。提交失败及同时又有新脏数据必须可恢复。两秒延迟在数据库健康无锁争用时测实际 HTTP 可见性；容量限制、长写事务和接管会影响真实完成时间。
- `collaboration_service.py:146,154` 在已确认提交及部分提交结果待核实的情形发送复查通知。`system_settings_service.py:88,121` 的 reload 和定时轮询负责取得当前库值。来自同一程序的心跳、重读与远程提示不能循环广播。无通道时，静默运行任务、仅 HTTP 的订阅、paused 任务和设置各自按明确期限复查；计时样例观察接收端的真实动作，收尾仍受 C3 原流程约束。
