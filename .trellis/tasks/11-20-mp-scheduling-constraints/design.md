# C2 跨进程调度与设置设计

本文记录开工时基于 0066 的设计。0067 的实际迁移行为、双进程观测和测试结果见[验收记录](research/verification.md)。

## 领取名额的生命周期

C1 已在 `main` 提供任务执行轮次、执行者租约、不可逆的失联确认和按收据接管。C2 要回答的是另一个问题：哪一次正常领取还在占用名额？例如，成功回调仍在处理自动分析时，下一章应继续排队；恢复进程接手旧任务做清理时，即使用户限额为零也须能完成清理。

| 场景 | 全局、用户、串行键和配额页的口径 |
| --- | --- |
| 进程预选候选，领取事务尚未提交 | 候选留在数据库队列，不预扣远端可见的名额。相同串行键的先后仍由队首保护。 |
| 正常领取已提交，包括提交确认迟到 | 从同一笔提交起，占一个全局名额、发起人的一个名额，以及该任务的非空串行键。确认结果前不可执行模型。 |
| 运行中，以及任务写成终态或暂停后、原执行体尚在做回调和收尾 | 原领取继续占用。不把任务显示的状态当作释放信号。 |
| 成功或失败回调已退出，原执行体完成 | 按原领取身份释放。旧业务凭据可能因收据、取消或清理失败继续保留，独立处理。 |
| 原执行者停止或已被 C1 确认失联 | 释放该执行者的占用。C1 恢复认领、旧版遗留任务、持久待核对任务本身均不新占名额。 |
| 暂停后继续、失败后重试、任务 ID 被重用 | 新领取有新身份。延迟释放上一轮只能命中上一份记录。 |

### 持久记录与迁移

在主库新增实例级 `task_execution_slots`（当前迁移头为 0066，拟用 0067）。每行保存原 `execution_key`、`worker_key`、`task_id`、稳定任务 UUID（`statistics_key`）、`queued_at`、实际 `user_id` 和可空 `serial_key`。以本次执行 UUID 唯一定位，确保同一任务 ID 不会同时获得两份有效占用。串行和总量仍在共用领取门内判定。存储冻结的用户及串行键，避免原任务被继续、裁剪或 ID 重用后依赖当前行反推身份。任务删除不能级联移除尚在执行的占用。

同一迁移在 SQLite 重建 `mcp_plugins` 以启用整数主键 AUTOINCREMENT，保留原插件 ID、列值、索引和约束。PostgreSQL 沿用原序列。插件地址检查、工具刷新在事务外等待，旧请求恢复后仍须重新确认原插件和连接目标。

- 成功领取的条件更新、章节或索引业务占用、统计和插入名额都在原主库事务提交。提交回执丢失时，新事务核对任务与占用的同一轮次，遇到暂时错误继续原有确认逻辑。不得重新计数、重复领取或重复发起模型调用。
- 释放在原执行体结束时进行，包括成功回调、最后的清理和必要的发布。收尾要能等待独立短事务，须覆盖正常、异常、取消和停机路径。按冻结的执行 UUID、worker 和原轮次删除，零行视为已释放。提交结果未知时重新按同一身份确认；临时不可写时保守保留名额并安排有界退避重试。停机排空收尾动作；失联后的遗留由 C1 的持久决定回收。
- 现有 `_running`、`_claiming`、hub 等继续维持本地取消、关停及订阅。领取后的全站占用只数持久记录；本地候选上限可限制本轮启动的协程数。数据库拒绝额度或队首检查后，等待下一次有意义的通知或定时重扫，避免完成回调立即唤醒同一堵塞候选形成忙循环。
- 以 C1 主库登记已停止或已围栏作为不可逆的释放凭据。SQLite 先在独立租约文件确认，再由 C1 向主库传播；PostgreSQL 等持锁事务结束再确认。一次心跳读超时、一个旧时间戳或缺失登记均不能证明可以释放。未确认期间保守保留，对端恢复及查询不改业务收据。将遗留占用随确认清理，并确保 C1 七天登记清理不会先抹掉释放所需的凭据。配额查询为只读；扫描和展示不触发接管。
- 0066 升级沿用父任务的停机约定。新表初始为空，旧 running 行由 C1 按原收据恢复。原生快照恢复沿用已有程序，新一代识别旧 worker 已被围栏，收回旧名额。作品 JSON 沿用 v16，更新 `app_schema`，导入导出均排除运行占用。降级在停机并确认无活跃占用后进行；活动、未知身份或无法确认时拒绝并保留表与版本。覆盖 SQLite 及 PostgreSQL 原位往返。

## 领取顺序和展示

1. `TaskEngine._dispatch` 仍按任务 ID 升序扫描，批量读取候选及占用只作预筛。较早同键候选因用户限额、业务凭据或暂时错误停滞时，继续保护队首。其他键仍可运行。
2. `_claim_and_run` 在现有 `AuthorizationRuntime → authz.gate → 用户 → 作品 → 任务 → 执行者` 的相对锁序内复查。领取门必须先于读取用于决策的事实；复用现有设置和配额写入已经持有的全局门。锁内读取最新全局上限、用户覆盖及所继承的默认值。用户显式不限仍受全局顶，显式零继续排队。调低上限时保留已经运行的任务，待占用降到新上限以下才放行。
3. 在该门内核对有效占用、同键占用、相同任务是否已占用，以及本轮候选之前是否仍有同键排队行。队首用持久 `id` 比较，复用派发已有的 queued、空执行键、无管理员取消标记以及作品生命周期可见条件；队首自身额度不足或本地退避不应将它从队首查询中排除。维持现有协作撤权、旧文档清理及管理员取消顺序。额度检查只保护向 running 的正常领取，不阻挡恢复。
4. 配额 API 使用同一持久占用口径。任务详情和列表原本按全站 queued 行、ID 升序、从零计算位次。队列进度帧统一该口径，去除广播时扣除本进程候选的差异。保留任务和协作者的可见性与投影；本次不负责跨实例广播。

## 系统设置

- 六个设置仍由 `SystemSettingsManager` 管理。取值次序为库内稀疏覆盖、实例启动时冻结的部署值、代码默认值。多实例部署使用相同部署基线；复位 `null` 和显式 `false` 必须可区分。双实例夹具须从同一份原始设置分别构建，避免把已发布的覆盖误当作另一端的部署基线。
- 每个服务实例定时检查持久 revision，正常存储和事件循环可用时，在一个调度周期（默认 5 秒）内把变化原子发布给原来的 Settings 对象，包括默认用户上限、全局并发、自动分析和开放接口限流阈值。采用独立于领取、恢复和长模型请求的定时任务，在应用/测试夹具中明确启动与关闭。锁顺序沿用 manager 锁 → 本地 runtime → 数据库。领取已持 runtime 时只就地读取数据库有效上限，不反向等待 manager 锁。无变化时避免反复 publish/notify；不确定状态须完整重读才能恢复，旧读取不得回写新发布。
- 复用现有更新的 revision CAS、成功审计同事务、提交确认丢失重读、错误矩阵和 `settings_confirmed`。缺设置行使用冻结的部署值，读取失败或持久值损坏时按既有安全错误处理并有界重试。公开 `/auth/config` 保留两开关、`no-store` 和既有前端轮询；可直接从同份持久快照返回。更新阈值保留原分钟计数，不重置限流，不新增第七项设置。
- 注册在实际建账号的事务中取得与设置保存有确定顺序的数据库门，核对持久开关后继续原账号创建、登录记录及会话签发。关闭先提交则返回既有 403，账号、登录记录、Cookie 均不产生。避免因慢密码哈希延长全站写锁，若将准备操作提前，实际写前仍须在锁内复核。
- MCP 插件路由的功能开关按持久值做短检查。插件管理保留已有能力和所有权检查；会修改插件的操作在实际提交路径内按一致锁序核验。刷新和试用在开始连接前、握手后发起工具发现或调用前，均按持久值复查。生产连接与 SDK 真实 HTTP 发送、分页和备用传输之间须有明确边界，避免用入口的布尔值授权后续调用。复用现有门禁和 HTTP 钩子，针对还未发出的业务请求核验，响应头或异常时释放短期发送保护。已经发出的调用允许完成；等待已有握手或流结束期间，另一实例须仍可提交关闭。保留智能体对真实工具调用的原身份和发送约束、现有 403 与异常清理。按登记的测试连接器和本机受控服务分别验收。

## 验收与部署边界

以两端同时拿到候选后才放行领取的方式验证并发、先后与唯一调用；控制事务提交、回调退出、设置关闭和网络发送的相对顺序。详细用例与命令见实施清单。C2 只覆盖领取名额、排队位次及六项设置。跨进程取消、实时订阅、全站排空和正式多进程部署仍按 C3–C7 验收，现有生产单进程约束继续适用。
