# C2 调度约束与系统设置跨进程一致

> 父任务：`.trellis/tasks/11-20-multiprocess-task-scheduling-deploy-drill`（总体设计见其 `design.md` 第 3 节）。
> C1（`11-20-mp-worker-lease`）已归档。执行者的停止或失联确认沿用 C1。C2 的占用生命周期见 [设计](design.md)，验证顺序见 [实施清单](implement.md)。

## Goal

让串行键、全局并发上限、每用户并发上限在所有进程合计的意义上生效；让系统设置的修改在其他进程生效，其中安全开关在下一次判定即生效。

## Background

- C1 合入后，调度预选仍数本进程的执行体、用户和串行键（`backend/app/services/task_engine/engine.py:824-875`，原 `engine.py:669-690`）。领取事务内也仍用本进程的已用量复核（`engine.py:1441-1448`，原 `engine.py:1261-1265`）。
- 领取事务已持有全局门 `authz.gate`（`authorization_service.py:105-127`），所有进程的领取在此串行，可以在门内读库判定。
- 用到串行键的类型：`chapter.analyze` 为 `analysis:{project_id}`，规范要求回写顺序与入队顺序一致（`.trellis/spec/backend/database-guidelines.md:560`）；`kb.index` 为 `index:{project_id}`。
- 同键先进先出目前依赖本进程的 `busy_serial` 与退避表 `_stalled`（`engine.py:839-865`，原 `engine.py:671-693`）。
- 系统设置由 `SystemSettingsManager._publish` 写进本进程的 `Settings` 对象，没有周期重载（`system_settings_service.py:60-69,93-109`）。注册入口只看进程内布尔值（`api/v1/auth.py:34`）；MCP 的插件管理、刷新工具、试用调用只看进程内开关并发起真实外连（`mcp/service.py:52-54,296-298,344-346`）；智能体真实发送已在发送事务内读库（`mcp/settings_gate.py:70-108`）。
- 配额页「已用并发」取本进程 `admitted_count`（`quota_service.py:83`）；`/auth/config` 返回进程内值（`api/v1/auth.py:26-29`）。

## Requirements

- **R1 全局并发上限按全站生效**。每次新领取都要有全站空余名额。按已提交且原执行体尚未完成收尾的正常领取计数，包括 R6 的回调阶段。调低上限后，已有占用可以暂时超过新值，降到上限以下才允许下一次领取。
- **R2 每用户并发上限按全站生效**：同上，按用户限额；限额为 0 时仍然禁止准入；降低上限不取消已运行的任务。
- **R3 串行键跨进程串行**：同一 `serial_key` 的任务不在任何两个进程同时运行。
- **R4 同键先进先出跨进程成立**：同键内 `id` 更小的可领取排队任务未被领取时，后面的同键任务不被任何进程领取；被上限挡住或无法前进的队首任务继续占住队首，与现有单进程语义一致。
- **R5 待核对任务不占名额**：已由恢复标记为待核对的运行中任务不计入并发与串行键占用。
- **R6 成功回调期间的占用语义不变**：任务写为成功后、成功回调结束前的名额与串行键占用，与现有单进程行为逐条对齐。
- **R7 安全开关即时生效**：一个进程关闭注册后，其他进程的下一次注册请求被拒；关闭 MCP 后，其他进程的下一次插件管理、刷新工具、试用调用被拒且不发起外连。
- **R8 其余设置有界收敛**：并发上限、每用户默认上限、自动分析开关、开放接口限流阈值在其他进程不超过一个调度周期内生效；`/auth/config` 随之一致。
- **R9 展示一致**：配额页的已用并发、任务列表的排队位次在任一进程读取结果一致。
- **R10 单进程兼容**。保留调度顺序、在途任务和设置保存的原有错误响应。领取已经提交但执行方尚未收到回执时，配额页即可显示占用。领取尚未提交时，排队进度帧仍将该任务计入位次，与任务列表一致。

## Acceptance Criteria

- [x] **AC1** 双引擎测试：上限为 2、排队 6 个任务，两个引擎同时调度，任意时刻运行中不超过 2。（R1）
- [x] **AC2** 双引擎测试：某用户限额为 1、排队 3 个任务，任意时刻该用户运行中不超过 1；限额为 0 时两个引擎都不领取；调高后恢复领取。（R2）
- [x] **AC3** 双引擎测试：同项目排队多个 `chapter.analyze`，两个引擎下逐个执行且完成顺序等于入队顺序。（R3、R4）
- [x] **AC4** 双引擎测试：队首同键任务因用户上限被挡时，另一个引擎不越过它领取同键后续任务。（R4）
- [x] **AC5** 待核对的运行中任务存在时，同键新任务与其他任务照常被领取。（R5）
- [x] **AC6** 阻塞成功回调时，两端均能读到该任务的占用，同用户、全局和同键的限制分别有效。收尾完成后，排队任务取得归还的名额。`tests/test_tasks.py` 的串行键与并发用例、`tests/test_rbac_concurrency.py`、`tests/test_user_quotas.py`、`tests/test_system_settings_runtime.py` 通过。逐项说明原内存计数断言如何改用可观察行为验证。（R6、R10）
- [x] **AC7** 双应用测试：在应用 A 关闭注册，应用 B 的下一次注册返回关闭提示；在 A 关闭 MCP，B 的刷新工具与试用调用被拒且假服务端没有收到请求。（R7）
- [x] **AC8** 在 A 修改设置，B 在一个调度周期内按新的全局与默认用户上限领取。自动分析的下一次派生和开放接口在同一分钟内的下一次限流判定也按届时已生效的新值执行。两端 `/auth/config` 返回相同开关。（R8）
- [x] **AC9** 在两次查询之间没有新领取或归还时，两个应用的配额页显示相同的用户占用，包含仍在成功回调中的正常领取，排除恢复接管和待核对任务。列表、详情与排队进度帧均按已提交的排队任务给出从零起算的位次。（R5、R6、R9）
- [x] **AC10** PostgreSQL 16 上串行通过 AC1–AC4 对应用例；SQLite 全量回归与 `ruff` 通过。

## Out of Scope

- 取消与删除排空（C3）。
- 排空开关（C6），它复用本子任务的设置读取方式。
- 调度扫描的分页或 `SKIP LOCKED` 优化：门内判定已保证正确，多进程只是多做无效尝试；若 C7 验收显示有性能问题再处理。
- 跨进程即时唤醒（C4 的内部通道）；本子任务以轮询周期为收敛上限。
